# 理解与深度审查

从仓库根读 `docs/README.md` 与 `docs/design/workflows.md#deep-review`、`#contract-verification`，按议题读取权威契约、相关完整源码及适用工程门禁。目标同时包含可理解的行为与有证据的正确性判断，不能用 AI 解释代替验证。

1. 固定范围和基线：明确比较提交 / 检出版本；工作区审查同时列出暂存、未暂存、未跟踪、新增 / 删除 / 重命名及生成物。每个变更文件记录所属审查单元、检查方式和状态，未审查或排除项给原因；沿路径读取必要未修改实现 / 消费者。必要时留内容摘要或快照。
2. 按跨文件行为组织：说明职责、入口出口、API / 依赖、状态所有权和副作用；复杂交互给源码定位的时序图，状态生命周期给图或表，说明分支、调度 / 通知、错误、重入、取消 / 失效和清理。标明源码推导或真实轨迹，不为普通文件强制完整图表。
3. 独立取证：先从契约及源码追踪所有相关入口，再核对作者说明与已有结果。问题记录触发条件、影响、契约依据、文件 / 符号 / 行号、证据类型及验证状态；将已证实缺陷、条件性风险、契约缺口、测试缺口分开。文件读过不等于行为已验证。
4. 验证：运行适用的现有命令；高风险反例明确输入、顺序及断言。只读审查不修改业务代码、测试或规范；新增反例交 W3 / W4，临时隔离探针需在已有授权内并说明范围。实际命令、结果与未执行原因如实记录，不降低断言或改规范迁就实现。
5. 收口：结束时复核基线，发生变化则重审受影响路径，未复核标过期 / 未验证。修复后的发现需在最终基线上复验后关闭。按 P0 / P1 / P2 列缺陷，其他风险 / 缺口另列；P0 / P1 未关闭、必需检查未通过或重要契约偏差未解决时暂缓合并。

完整输出遵循工作流的报告结构：结论 / 发现 → 基线 / 文件覆盖 → 模块理解 / 执行模型 → 契约一致性 → 实际证据 → 后续动作与残余风险。只在任务或既有 PR 交付，不默认建报告文件。无发现只说明本次范围未发现，不推断全局无缺陷。

高风险变更在已有授权及可用能力下优先独立上下文审查，输入原始材料与验证入口，不输入预设结论。无法独立执行时披露自审及限制；独立上下文不保证消除共同盲点。不以选中 skill 推导多 agent、外部消息、合并或发布授权。

例如最终状态测试通过仍不能证明稳定后通知：定位全部适用通知调用，并检查观察者所见状态 / 顺序；没有实际执行结果时标为源码事实或推断，不能记作运行通过。真正语义缺口集中交 `form-design`，仅暂停相关范围；实现偏差交已授权 `form-debug` / `form-delivery`，单独审查本身保持只读。
