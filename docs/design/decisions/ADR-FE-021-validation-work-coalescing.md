# ADR-FE-021：统一校验队列与有效在途任务复用

## 背景与决策理由 {#adr-021-context}

先前 Runtime 每次完整调用直接执行一套 `run(true)`，撤销同来源的现有请求并重启。自动增量与完整调用重叠、连续调用完整校验时，这会重复启动仍有效的任务。审查另用业务订阅回调主动调用 validate 的反例复现同步重入：内层调用启动新请求后，外层遍历仍可能撤销它。普通订阅同步执行，Reaction 只入队；该反例没有引入协程、线程并行或网络等待阻塞。用户明确把这个反例归为低优先级优化输入，后续提出将新需求加入当前队列、调整未执行部分的顺序并去重。

2026-10-26 用户确认实施“统一执行入口 + 合并排队需求 + 复用有效在途任务”，同时要求保存决策思路。收益目标是减少重叠需求造成的重复启动、撤销和发布；不将单次孤立校验的计算量、真实网络请求数或生产耗时改善作为未经测量的承诺。

## 已确认选择 {#adr-021-decision}

1. 自动增量与完整调用共用来源队列和同步执行入口。运行中新增需求只登记，不递归开启另一套 Runner；只补齐未执行任务及同步前置。根 Schema 优先，其他规则沿用稳定顺序及前置资格，不增加固定的全同步 / 全异步两阶段或业务优先级。
2. 工作按规则身份与具体 Scope 实例隔离。尚在队列、同步检查中和有效网络等待中的工作可以合并；复用在途请求仍检查本次 when、同步前置、来源与请求代次。不同成员不能去重成同一任务，输入 / Context / 实例失效规则保持。
3. 完整调用独立保存调用号、输入快照和要求覆盖的工作。新完整调用使旧调用返回 stale，但不因此撤销仍有效的共享任务；最新调用等待自己要求的全部工作，不只等待登记时已出现的 Promise。
4. 同一次执行中的同步前置去重，历史通过不替代本次前置检查。已完成的外部结果不跨完整调用缓存；新完整调用允许重试已完成来源，即使其他来源仍在途。结果正在发布时也视为已经有终态，不把回调主动重试误合并回旧失败结果。
5. 来源结果继续独立发布与字段聚合；合并需求本身不清空已有 Issues 或再次发布 pending。真正失效或重新执行的来源按原有生命周期更新。外部请求不阻塞后续同步规则，完整调用才等待全部适用异步义务。
6. 调用结束解除其工作关联并封存诊断，不保留已结束的调用收集器或 FlushContext。共享任务保留真实启动输入与 origin，`relatedCalls` 关联正在等待它的完整调用；复用任务失败也必须进入最新调用的完整诊断。
7. 一次同步入口只消费当前交接批次；新追加工作通过已有 Scheduler 继续处理，不能在私有无限 drain 中绕过 Flush 预算。合并需求不重置预算。

这细化 ADR-FE-010 的任务新旧调用边界：完整调用被取代与来源任务真正失效分别处理；真正替换任务时仍先撤销旧结果资格，再尽力取消网络。没有替代 Schema / Constraint 分责、状态所有权或独立完整证明契约。

## 取舍与后续候选 {#adr-021-tradeoffs}

相较每次完整调用都重启请求，统一队列减少有效在途工作的重复执行；代价是显式区分来源、执行工作和调用等待，完整结果必须按工作覆盖收口，诊断也须支持共享任务关联。

本轮不引入已完成结果缓存、全字段状态树或字段查询索引。已完成外部结果缓存可能改变重试及服务端新鲜度语义；字段聚合索引还会增加多目标 Issue、Scope 生命周期和查询缓存的一致性维护成本。用户认为目前没有必要，要求仅保留设计优化点。未来有真实瓶颈时，再测量 Host 校验器启动 / cancel 次数、规则和 Schema 执行次数、来源发布 / 字段查询量、保留内存及完整校验耗时，然后独立选择是否实施，不预先确定阈值、缓存有效期或新 API。

## 实现与验证范围 {#adr-021-evidence}

TS Runtime 使用 `ValidationManager` 的唯一同步入口、按来源去重的 Pending、`ValidationWork` 与 `ValidationCall` 表达以上边界。反例与验收入口为 `packages/runtime/tests/validation-queue.test.ts`，覆盖连续完整调用、pending / Schema 发布重入、共享错误归属、已完成结果重试、成员隔离 / 删除及前置失效；运行方式和当前限制见 [Runtime Review 入口](../../../packages/runtime/README.md)。用例通过不代表跨端、浏览器交互、生产网络和目标设备性能验收完成。
