# ADR-FE-027：平台采用 DDD 思路的模块化单体

## 背景与选择 {#adr-027-decision}

平台蓝图与单团队 RBAC 已确认，页面、业务对象与生命周期仍待逐项设计。用户要求先划大方向，再展开模块；比较按业务对象直接拆微服务与先建立业务边界的模块化单体后，明确采用 DDD 思路做模块化单体，首期不拆微服务。

采用 DDD 梳理职责、业务规则和数据所有权，一个前端应用承载 Platform / Studio，一个 API 部署承载领域模块。以成员访问、表单创作、能力资产、构建发布、问题治理五块职责作为细化起点，不将页面或业务对象直接映射为服务。模块通过明确公开接口协作，数据由所属模块负责写入；核心引擎包保持独立。

## 取舍与限定 {#adr-027-consequences}

单一部署降低跨网络协调与初期运维成本，但模块不能独立部署，资源隔离和扩容需要后续按真实负载演进。用模块封装与数据所有权避免单体内部任意耦合；不承诺仅凭目录就已满足隔离，也不预建消息总线、事件溯源或复杂通用领域框架。

完整职责、发布协作、演进条件与细化顺序见[整体架构](../architecture.md#platform-modular-monolith)。构建 Worker 等按需评估，不视为首期服务；具体限界上下文、聚合、数据库、接口与事务待设计。下一专题为表单创作管理的模型、状态及列表 / 工作台流程；本次未修改实现或引擎契约，不替代 ADR-FE-013 / 014 / 026。
