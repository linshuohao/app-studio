## 逐层设计顺序

1. Definition：先能力需求，再核心抽象及关系，最后协议组织。
2. Runtime：数据模型、状态、作用域、身份与生命周期。
3. Runtime：依赖计算、命令、事务、校验与异步资源。
4. Preparation：根据运行时需求设计预处理、索引与诊断。
5. Renderer / Material / Capability：跨端绑定与扩展契约。
6. 版本、工具与工程治理。

L1 先形成《能力需求与抽象边界》，逐项比较数据与视图、表达式、校验、联动、引用作用域和配置复杂度，收敛后再形成《领域元模型与协议规范》。MVL / Data-View-Logic 保留为候选组织方式，不预先接受或否定。

每个专题逐篇形成，记录目标、模型、接口、机制、取舍及验收。新增专题时更新首页导航，专题提供返回文档首页与架构基线的链接；影响整体边界的决策同步更新基线。决策区分 Proposed / Accepted / Rejected / Superseded。

下一轮：评审草稿的定义分类、组合契约与默认语义，用代表性多端与校验联动场景验证，再收敛最小元模型。业务资料作为实现和验证输入，不阻塞 L1 草稿推进。
