01

产品能力边界

我们建设的是复杂动态表单与数据录入引擎，不是通用页面搭建器、任意逻辑编排平台或完整 BPM 系统。所有原生能力都应服务于表单式数据交互。

能力范围处理方式原因
字段定义、数据绑定、布局分组引擎原生表单基础能力
条件显隐、必填、禁用引擎原生高频且容易标准化
跨字段计算、动态校验引擎原生复杂表单核心价值
嵌套对象、动态数组、重复区块引擎原生需要统一状态及身份管理
初始化、批量赋值、重置引擎原生需要统一执行语义
异步选项、远程查询、业务校验核心调度 + 外部能力通用生命周期与具体业务解耦
分步骤表单轻量原生无需完整工作流引擎
自定义复杂业务字段物料扩展隔离领域特殊性
报价、核保、审批宿主业务服务保留权威业务状态
任意页面搭建、营销动效、通用 BPM明确不在范围成本与核心目标不匹配
边界决策

仅为“表单式数据交互”提供完整执行语义。被保人录入、条件联动、异步报价预览属于系统范围；审批、支付、生成保单等跨系统业务流程属于宿主系统。

04

L1 · Definition：领域模型与协议层

这是需要最谨慎设计的一层。它决定配置者需要理解多少概念，以及增加新业务能力时是否会不断破坏协议。

4.1 服务对象与核心目标

服务对象真正需要的能力
业务配置者简单地定义字段、条件、联动和校验
可视化设计器编辑、定位、组合和验证配置节点
Preparation将声明转成可执行的规范化形式

优先追求语义清晰、易于配置、可静态检查，不以“最少字段”或者“任意编程能力”为首要目标。

L1 设计顺序已调整

先能力建模，再概念建模，最后协议建模。下文的五个概念域与推荐方案是历史候选思路，不限定最终元模型或顶层结构；MVL / Data-View-Logic 仍可参与比较。详见 《L1 能力需求与抽象边界》。

4.2 五个候选概念域（待比较）

Form Definition Domain Model

Form Definition

一个可独立实例化的表单定义

↓

Data

字段类型、数据结构、静态约束

Structure

分组、步骤、布局、控件节点

Expression

条件、比较与纯计算

Constraint

业务约束与数据校验

Resource

外部数据能力及其引用

Data 和 Structure 在语义上应该分离，但在配置界面中可以统一编辑。配置者添加一个“年龄输入框”，工具可以同时创建数据字段和组件节点；底层两者具有不同身份。

这可以覆盖一份字段被多个组件消费（输入框与摘要），以及一个组件绑定多个字段（日期范围、地址组合）的场景，避免数据结构被 UI 组件限制。

4.3 本层的核心取舍

设计问题备选方案当前倾向
数据与视图一体化 / 完全分离语义分离，设计器可合并编辑体验
字段表示组件即字段 / 独立数据字段独立 Data Field
表达式字符串 DSL / 结构化 AST待比较字符串、AST 及纯函数扩展，不冻结表示方式
联动全部事件规则 / 声明式条件简单状态用声明式派生
复杂业务持续扩张 DSL / 注册能力受控 Capability 扩展
布局任意页面树 / 表单容器仅支持必要表单结构
标准全自研 / 全部采用 JSON Schema复用数据标准，独立建模交互

4.4 配置友好，内部语义严谨

配置者只需表达：“当年龄小于 18 岁时显示监护人姓名，并要求填写。”底层要区分展示条件与数据合法性。

Semantic Example / 简化表示
guardianName.visibleWhen = age < 18

Constraint:
  if age < 18
  then guardianName must not be empty

显隐是 UI 派生，约束是可独立执行的数据合法性规则。后者不能只放在控件 `required` 属性中，否则服务端绕过 Renderer 无法进行同语义校验。

4.5 明确不负责什么

Definition 描述业务含义，不描述 Runtime 的内部队列、Dirty Set、事务波次、网络调度器或 UI 订阅细节。

需要尽早统一的语义

字段不存在、undefined、null、空字符串、空数组应有清晰的初始化、比较和提交规范，不能交给不同组件或平台自行决定。

05

L2 · Preparation：定义预处理层

先不把它设计成完整编译器。它的核心职责是：把易编辑的 Form Definition 安全、稳定地转换成 Runtime 可直接消费的 Prepared Form。

5.1 服务对象

直接服务 Runtime、配置设计器、发布构建流程与测试工具。业务配置者主要消费它输出的诊断结果。

5.3 复杂度取舍

问题V1 方案暂不引入
解释 vs 预处理加载时准备一次每次联动重新解析配置
编译深度Normalizer + Analyzer + Indices完整代码生成与重型优化器
依赖关系预提取表达式依赖通用动态依赖语言
物料检查检查标识、版本和接口执行物料内部代码
循环检查检测纯计算环并报错默认支持固定点求解
产物缓存按版本与内容 Hash 缓存复杂编译集群

例如 500 个字段和 200 条表达式的表单，Runtime 应能根据预处理索引找到受影响节点，而不是字段每次变化都扫描整份配置。但性能收益必须实测。

边界：Preparation 不是第二套 Runtime

Prepared Form 可以包含字段定义、表达式、依赖索引、物料和资源引用，但不能包含用户输入、焦点、错误状态、请求状态和当前会话。一个 Prepared Form 应允许多个表单实例安全复用。

06

L3 · Runtime：最值得投入的核心

真正的技术差异化应该集中在复杂表单的状态一致性、依赖传播、动态数组、时序和异步边界。但 Runtime 不能演变成泛化的业务逻辑平台。

State Store

数据值与运行时状态，统一读写和订阅。

Scope & Identity

动态数组、重复区块、稳定实体身份。

Dependency & Rules

纯计算、脏依赖收集和增量传播。

Transaction & Commands

操作意图、批处理、稳定态与原子提交。

Validation

静态约束、动态条件、同步与异步校验。

Resources & Lifecycle

异步资源、并发竞态、实例生命周期。

6.1 State Store：业务状态的权威来源

状态示例通常属于提交数据？
Data年龄、姓名、目的地是
DerivedisMinor、汇总人数取决于数据契约
Field Metavisible、disabled、readOnly否
Validationerrors、校验中否
Interactiondirty、touched否
Resourceloading、error、data通常不直接提交

推荐：业务数据与运行时元状态分开保存，通过统一 Field Snapshot 向 Renderer 提供。默认由 Core 拥有数据容器，受控写入；事务内记录变更，不要求从第一版开始实现完全不可变的深层数据结构。

待取舍：数据所有权、可变/不可变策略、快照缓存、路径寻址、订阅粒度以及字段状态生命周期。

6.2 Scope & Identity：动态数组不是普通 splice

Scope Tree / 字段实例身份
Form Session
└─ insuredList
   ├─ Item ID: a1
   │  ├─ age
   │  └─ guardianName
   └─ Item ID: b2
      ├─ age
      └─ guardianName

数组项身份必须与 index 分离：删除第一项后，第二项的当前路径发生变化，但其字段错误、交互状态和组件实例身份不能串项。

Field Identity = Scope Identity + Field Definition Identity

当前 Data Path 是可变的地址投影，不是永久字段身份。模块负责数组增删移动、嵌套作用域、字段注册销毁及相对路径解析；Renderer 消费稳定 ID，使用自身框架机制维护组件身份。

6.3 Dependency & Rules：纯计算优先

Dependency Graph · Example

age

用户输入数据

↓

isMinor = age < 18

纯派生计算

↓

guardian.visible

展示状态

guardian.required

约束 / UI 投影

高频、确定性的字段联动优先使用纯计算模型，而不是事件触发的命令链。表达式求值时不应发请求、埋点或任意修改其他数据。

设计点建议
依赖追踪静态依赖优先，数组实例形成作用域引用
全量与增量初始化建状态，后续增量计算
同步与异步纯计算同步，异步交给 Resource
传播模型脏节点集合与明确求值顺序
循环处理静态尽早拒绝，运行时兜底熔断

同一数据目标被多个纯派生规则写入应被视为潜在冲突，在 Preparation 阶段报错或要求显式归约规则，不能依赖偶然执行顺序。

6.4 Transaction & Commands：统一状态变更边界

Synchronous Transaction
Command
→
Open Transaction
→
Apply Changes
Collect Dirty
→
Recompute
→
Check Invariants
Commit
→
Notify Subscribers

Transaction 保证一次相关同步变化的一致性；Command 保留用户操作的因果、顺序和次数。两次添加被保人不能因为目标路径相同就合并成一次。

  • 批量初始化不产生无效中间传播。
  • 同一派生节点避免通过多条路径重复无效求值。
  • 同步事务失败不对外暴露部分提交状态。
  • 提交后订阅者读取到稳定的一致状态。
  • 外部 I/O 不属于可原子回滚的本地事务范围。

暂不引入重型通用 Scheduler；先解决批量、确定性、异常回滚和准确通知。

6.5 Validation：合法性不能只依赖 UI

Validation 应覆盖静态类型格式、条件必填、跨字段约束和必要的异步业务校验，并复用 Definition 的数据约束语义。

UI 投影

红色必填星号、错误文案、字段校验中状态，用于即时交互反馈。

服务端权威

动态业务约束仍必须由服务端执行或验证，不能因 UI 已校验就信任提交。

隐藏字段的保留、清空与提交排除策略必须显式定义；Renderer 不得根据“不可见”擅自删除业务数据。

6.6 Resources & Lifecycle：受控异步与实例生命周期

Async Race · 后发先至
destination = JP
  → requestQuote(JP)   // request A

destination = SG
  → requestQuote(SG)   // request B

A 的响应晚于 B：
  → 已过期，不得覆盖当前报价

Resource Manager 负责失效、取消、并发去重、加载、超时与错误状态；外部业务 API、认证和业务响应由 Capability 实现。

Runtime 同时管理初始化、Ready、提交和销毁等生命周期。可以内置轻量分步表单状态，但不内置完整 Workflow Engine。

Runtime 原生负责明确不负责
字段值和元状态业务数据库持久化
局部同步计算长生命周期审批流程
交互命令与本地事务跨系统分布式事务
校验调度最终业务权限与风控决策
异步资源生命周期具体报价业务算法
字段与表单实例生命周期DOM 及具体 UI 框架
Runtime 应是技术能力最强、同时职责边界最严格的一层。
07

L4 · Renderer：呈现与交互适配层

Renderer 应当轻量，但不能薄到只有 componentMap[name]。真实组件还需要管理值适配、输入事件、校验呈现、订阅、焦点与框架生命周期。

7.1 主要服务对象与模块

服务最终填写表单的用户，以及集成 UI 组件库的开发者。对开发者提供稳定的字段接入接口，而不是暴露 Runtime 内部依赖图。

模块职责
Form Renderer根据结构组织整体 UI
Field Controller字段状态和组件事件适配
Component Registry语义组件 ID 到具体实现的映射
Layout Renderer分组、步骤、布局和容器
Scope Adapter重复区块的当前数组项上下文
Platform Adapter框架订阅、生命周期及交互差异

7.2 Field Controller 候选接口

TypeScript / Interface Sketch
interface FieldController<T> {
  readonly id: string

  getSnapshot(): FieldSnapshot<T>

  subscribe(listener: () => void): () => void

  change(value: T): void
  blur(): void
}

Field Snapshot 应由 Runtime 提供当前值、控制元状态和校验信息。组件的 change 与 blur 转换成受控交互意图，而不是直接修改内部 Store。

7.3 关键取舍

问题建议理由
通用 UI 树 vs 分端定义统一表单语义，允许端侧呈现覆盖兼顾一致性与平台体验
组件直连 Runtime优先通过 Field Controller降低耦合
Renderer 保存字段值不持有第二套业务权威状态避免状态分裂
Renderer 局部状态允许焦点、输入法组合态、弹窗等
组件与字段关系不要求一一对应支持组合控件与摘要展示
首版多端支持先支持主目标端验证契约控制交付成本
更新方式字段级订阅 / Selector减少全表更新

Renderer 可以维护输入法组合期间的临时文本、日期选择过程等局部状态，但必须规定提交和取消语义，不能变成第二份业务真相。

7.4 跨端一致性的范围

必须一致允许不同
值类型与序列化控件视觉样式
校验规则和结果错误展示形式
条件显隐语义页面布局
数组身份与操作语义原生组件实现
提交数据结构动画及细节交互
异步资源状态语义加载反馈形式

跨端的首要标准是同一语义定义得到一致的业务结果，而不是不同端必须复用相同源码或像素级一致。Flutter/Dart 可能需要桥接或独立执行实现，用契约测试验证。

Renderer 边界

Renderer 决定如何呈现和交互，不自行解释业务条件，不因隐藏而擅自删数据，不绕过 Runtime 修改表单权威状态。

08

Material：物料体系与 UI 扩展

物料不是执行链中的单一层：设计器需要它的元信息，Preparation 需要检查它的契约，Renderer 需要加载它的平台实现。

8.1 V1 的物料范围

物料类别示例主要服务对象
基础字段Input、Select、DatePicker配置者
结构与容器Section、Tabs、Steps、Repeater设计器、Renderer
领域业务字段证件上传、被保人卡片、地区选择业务团队

自定义纯函数、远程资源和业务命令更适合放进 Capability Registry，不必因为它们可复用，就全部塞进 UI Material Registry。

8.2 物料契约草案

TypeScript / Material Definition
interface MaterialDefinition {
  id: string
  version: string
  propsSchema: unknown

  bindings: BindingContract[]
  events: EventContract[]
  platforms: PlatformSupport[]

  capabilities?: string[]
  editor?: EditorMetadata
}

bindings 声明支持的数据绑定，例如日期范围的两个字段；events 声明用户事件；platforms 声明目标端实现；editor 定义属性面板元信息。

8.3 必须做出的取舍

问题建议
能否访问 Runtime 内部不可以，必须通过受控接口
是否支持复杂领域物料支持，但要求明确契约
是否建立通用插件生命周期按真实需求实现最小生命周期
物料能否注册业务逻辑通过 Capability 接口
是否默认全动态加载根据发布模式选择，不设为默认
是否建设独立物料市场第一版不需要
核心边界

基础物料是具有数据绑定能力的 UI 组件；复杂领域物料可以封装局部交互，但最终业务值必须通过明确的绑定契约交付 Runtime，不能把关键状态长期藏在组件内部。

09

Capability：外部能力与业务集成

Runtime 管理外部调用的生命周期，而宿主负责具体外部调用。二者不能混为一谈。

Resource / Capability Boundary

Form Runtime

发起报价资源请求

↓

Capability Adapter

参数映射 · 接口鉴权 · 服务调用

↓

Business Service

计算并返回业务结果

↓ Result

Resource Manager → Form Runtime → Renderer

检查响应是否过期 · 更新资源状态 · 呈现结果

Capability典型场景
Query / Resource城市列表、报价、搜索结果
Upload证件采集、图片上传
Business Command保存草稿、提交录单、确认报价
Context Provider用户、地区、渠道上下文
External Validation身份校验、资格校验

插件不应无约束地拿到完整可变 Store；应通过参数、只读快照、受控回灌和执行结果协议协作。客户端的能力注册更不是服务端权限校验的替代。

关于 Workflow

表单局部交互、分步录入和异步查询不需要完整工作流引擎。审批、核保、支付等长流程通过 Capability 调用外部 Workflow Service；不将它放入表单 Runtime。

10

Tooling：设计器、调试器、发布与治理

先解决定义和运行时语义，再投入复杂拖拽设计器。第一阶段优先实现 Definition Editor + Preview + Runtime Devtools，降低验证成本。

阶段工具直接价值
阶段一Definition Editor、Preview、Diagnostics快速验证协议与运行时
阶段二Rule Builder、Runtime Trace降低逻辑配置与调试成本
阶段三可视化 Form Studio降低业务配置门槛
阶段四Release Console、Material Manager规模化交付与治理

10.1 版本从第一版开始治理

版本对象意义
Definition Revision具体表单业务定义的修订
Definition Format Version协议格式与语义版本
Runtime Compatibility该表单需要的执行能力
Material Versions所依赖的物料及其版本
Data Contract Version草稿与已保存数据的结构版本

发布表单应形成不可变 Release Artifact，默认让运行中的会话固定已发布版本，避免中途变更计算语义。配置迁移与历史草稿数据迁移应分开处理。

10.2 工程质量保障

静态质量

引用检查、类型校验、物料能力验证、规则冲突与依赖环分析。

运行时质量

事务一致性、竞态防护、动态数组、资源释放、错误隔离。

跨端契约

同一输入在不同端产生相同数据与规则结果的 Golden Tests。

发布与可观测性

不可变版本、灰度回滚、因果链 Trace、性能指标和脱敏日志。

11

完整案例：保险投保表单的一次交互

通过真实业务流程验证各层边界。假设表单包含目的地、投保人、被保人列表和动态报价。

Interaction Timeline / End-to-End
01

初始化定义

Runtime 消费 Prepared Form，建立数据、字段身份和依赖索引。

02

建立初始稳定态

批量回填表单数据，计算派生值和约束，再向 Renderer 发布一致快照。

03

用户修改被保人年龄

Renderer 发送 SetValue 意图；Runtime 开启事务，写入数据并收集受影响依赖。

04

规则计算并提交

计算监护人显隐与校验规则，提交稳定状态并通知受影响的组件。

05

发起异步报价

Resource Manager 使用 Capability 调用报价服务；只接受仍属于最新有效依赖状态的结果。

06

报价更新至页面

资源结果重新进入 Runtime 更新流程，Renderer 读取新的稳定快照并展示。

Cross-layer Call Sequence
Preparation → Prepared Form
Runtime     → Init / Batch Derive / Commit
Renderer    ← Stable Field Snapshots

User        → Change insured.age
Renderer    → Dispatch SetValue
Runtime     → Transaction / Dirty Dependencies
Runtime     → Validate / Commit
Renderer    ← Changed Field Notifications

Runtime     → Request Quote via Capability
Capability  → Business Service
Business    → Quote Response
Runtime     → Freshness Check / Accept Result
Renderer    ← Updated Quote Snapshot

全链路没有独立 Workflow Engine，也没有通用的双向 View-Logic 桥接平台，却能满足复杂表单的状态一致性、联动、竞态防护及跨端渲染需求。

过度设计判断标准

如果引入一个新模块、协议概念或调度机制，既不能提升这类主路径的可靠性、交付效率、性能或可维护性，也没有可靠的扩展收益，就需要重新评估其必要性。

12

六大设计方向映射到各层

六个方向不是六个纵向层级，而是贯穿各层的设计与评审维度。

设计方向主要涉及层次核心问题
协议灵活度与复杂度Definition + Preparation简单配置简单，复杂场景可组合
逻辑编排与运行时Runtime状态如何稳定计算、提交与恢复
跨端一致性Definition + Runtime + Renderer哪些规则共享，哪些视图与行为按显式策略差异化
物料与扩展性Material + Renderer + Capability业务扩展不侵入核心
版本兼容与演进Definition + Preparation + Tooling历史配置、数据与依赖长期可用
工程治理与质量所有层每个关键语义可验证、可追踪

必须警惕的跨层破坏

协议任意 JS

可能破坏跨端语义和静态分析能力。

物料直接写 Store

可能绕过事务与状态一致性。

索引不带版本

可能破坏缓存、发布及回滚正确性。

Renderer 自算业务

导致各端规则漂移与权威数据分裂。

13

架构决策清单（ADR 基线）

明确哪些产品决策已经收敛，哪些仍然需要独立专题进一步比较，不把建议误认为最终方案。

决策当前建议状态
产品范围复杂动态表单与数据录入已确定
通用页面搭建不作为核心目标已确定
完整 Workflow Engine不内置，按需集成已确定
核心执行层次Definition / Preparation / Runtime / Renderer已确定
状态所有权统一归属 Form Runtime架构基线
字段与 UI 节点逻辑分离待建模
协议表达受限声明式 DSL待比较
Preparation 深度轻量标准化与静态分析待设计
计算模型纯派生 + Command + Resource待论证
Store 实现Core-owned、事务化写入待比较
动态数组身份稳定 Scope / Item ID架构基线
物料与 Capability分离扩展契约待设计
跨端策略统一语义契约、适配不同实现架构基线
设计器投入先验证运行时，后扩展可视化建议基线
版本与质量保障从第一阶段同步纳入必须具备

后续每项决策可记录 Proposed / Accepted / Rejected / Superseded 状态，并保留决策背景、替代方案、代价和触发重新评估的条件。

14

逐层讨论与详细设计路线

不是同时推进所有层，而是从领域模型和状态语义出发，逐步推导实现机制。每一轮讨论都输出职责、接口、取舍、失败路径和验证方式。

01

Definition：能力 → 抽象 → 协议

先确认 L1 能力需求，再比较核心概念与关系，最后组织协议。MVL 保留为候选表示。

产物：能力需求与抽象边界 → 领域元模型与协议规范 → 典型场景验证
02

Runtime：数据模型与状态管理

讨论 Store、Field State、Scope、Identity、Snapshot、初始化和生命周期，统一数据语义。

产物：数据结构、状态 API、生命周期规范
03

Runtime：计算、命令与事务

讨论依赖追踪、增量传播、批量事务、循环、校验及异步资源，验证复杂联动与竞态。

产物：执行流程、调度算法、时序图、异常边界
04

Preparation：静态分析和执行准备

理解 Runtime 实际需求后反推最小预处理层，明确依赖索引、诊断和 Prepared Form。

产物：Prepared Form 结构、规则索引、诊断规范
05

Renderer / Material / Capability

明确跨端 UI 绑定、组件接口、物料注册、宿主能力与业务扩展的职责边界。

产物：Adapter Contract、Material Manifest、Capability API
06

版本、工具与工程治理

完善迁移、测试、设计器、发布、性能和可观测性，并通过真实业务用例进行回归验证。

产物：版本模型、测试矩阵、发布规范、实施路线
为什么 Preparation 详细设计排在 Runtime 后面？

需要先确认运行时实际的索引和执行模型，否则容易为“完整编译器”过度设计无用的中间结构。Definition 与 Runtime 应迭代验证，而不是先冻结整份协议。

每一个专题的统一讨论模板

01 · 目标与对象

解决什么问题？为谁服务？有什么明确非目标？

02 · 模型与职责

有哪些实体、状态、不变量？内部如何分层？

03 · 接口与数据流

输入、输出、生命周期、版本和错误契约。

04 · 核心机制

典型业务的流程、时序、算法及伪代码。

05 · 方案取舍

为何选择某种方案？替代方案的代价是什么？

06 · 验收与演进

边界、失败路径、性能、测试和未来扩展。
