01

已确定的基线与待讨论的内容

本专题承接整体架构 V1。总体分层保持不变，L1 的能力、概念及协议组织重新按顺序论证。本文建立需求清单和比较框架，具体候选方案仍为 Proposed。

状态内容
Accepted · 已确定产品定位为复杂动态表单与数据录入引擎；保留 Definition → Preparation → Runtime → Renderer 四层，以及 Material / Capability 和 Tooling 的职责边界。
Accepted · 已确定需要定义数据、视图和动态行为；不建设通用页面引擎和完整 Workflow Engine；兼顾配置简单性、复杂业务表达与跨端一致性。
Proposed · 待比较Field / DataNode / ViewNode 的抽象、表达式表示、约束组织、联动原生语义、引用作用域、复用与扩展。
Proposed · 待比较MVL / Data-View-Logic、fields-layout-rules-resources 等协议组织；是否需要简化配置与规范化协议两种表示。
对前一轮提案的定位

Data、Field、ViewNode、Binding、Scope、计算声明等是候选抽象，不是已经接受的元模型。表达式 AST、字段与视图分离、独立动态约束等也需要方案比较。MVL 保留为候选组织方式，不预先接受或否定。

03

L1 能力需求清单

编号 / 能力需要表达的业务语义验证样例职责边界
A01 · 数据定义类型、对象、嵌套数组、默认值，以及缺失与空值的含义。被保人列表包含多个地址；草稿加载时保留已有值。L1 声明结构和默认策略；L3 建立实例和初始化状态。
A02 · 视图定义组件、布局、步骤、绑定及动态展示。年龄同时出现在输入框与摘要；日期范围关联起止日期。L1 表达结构和关联；Material 提供物料；L4 适配呈现。
A03 · 动态计算条件判断、跨字段计算、集合汇总、派生状态及复用。未成年人条件、总人数、同一条件用于显示与校验。L1 声明输入与结果语义；L2 分析依赖；L3 求值。
A04 · 数据校验基础约束、条件必填、跨字段与集合校验、外部业务校验。结束日期不早于开始日期；证件号不能重复。L1 描述合法性及错误关联；L3 执行；后端仍维护权威校验。
A05 · 联动行为变化后的清空、赋值、重置与数组操作；说明何时发生。国家变化清空城市；点击添加新增被保人。L1 声明触发条件和操作意图；L3 负责事务和调度。
A06 · 外部数据远程选项、查询、异步校验的参数、触发及结果使用。根据国家加载城市；按投保信息查询报价。L1 引用外部能力；L3 协调请求；Capability 执行业务调用。
A07 · 表单交互初始化、分步操作、校验、重置、提交入口及其范围。回填草稿、下一步前校验、保存草稿、正式提交。L1 表达局部交互意图；L3 执行本地语义；宿主处理业务提交。

能力边界

L1 可以声明“国家发生有效变化后清空城市”，但不定义脏队列、事务波次、并发调度器或组件订阅机制。外部审批、支付及跨系统长流程由宿主能力承接。

需要纳入清单的横向语义

空值、隐藏与数据保留、默认值与回填优先级、计算值是否允许覆盖、错误关联、操作触发来源、数组身份、资源结果失效与提交范围，都必须在后续专题中明确，不能由组件各自解释。

04

候选概念与独立性判断

候选概念覆盖的能力是否独立的判断问题
Data / Field / DataNodeA01、A02、A03、A04是否需要字段独立身份？对象、集合、标量是否共享数据节点模型？是否造成双份结构维护？
View / ViewNodeA02、A07一字段多视图、多字段组件、无绑定节点、无视图数据如何覆盖？独立程度是否值得配置成本？
Reference / Binding / ScopeA02 至 A06绑定与计算引用能否共享寻址语义？哪些只需内嵌值，哪些需要身份、生命周期或复用？
ExpressionA02、A03、A04、A06是否能统一条件、计算、约束谓词及参数？领域函数的依赖是否可分析、语义是否可跨端实现？
ConstraintA04基础约束与动态约束怎样组合？约束目标、触发条件、错误位置是否需要独立声明？
Event / Command / RuleA05、A07事实通知与操作意图如何区分？最小联动语义是否足够，还是需要受限组合？
ResourceA06查询、异步校验、上传与业务命令有哪些共性，哪些不能共享自动重执行语义？
Computation / 命名表达式 / 计算声明A03是求值实现、表达式复用还是目标值归属？是否存在表达式加绑定无法覆盖的独立语义？
新增概念的准入条件

只有当它具有其他概念组合难以表达的业务语义，或明确需要独立身份、复用、生命周期、诊断定位时，才考虑成为独立对象。内部执行模块不自动对应用户可见概念；有业务语义也不自动意味着顶层目录。

Expression 与 Computation 暂不作为两套配置语言。后续分别检查“纯表达能力”“命名复用”“结果写入目标”是否可以组合表达，再决定需要哪些名称和结构。

05

六个关键取舍：比较议程

以下是比较起点，均未选定最终方案。它们不一定互斥；先比较各维度，再判断哪些可以组合。评估项是待验证的设计风险，不是已经完成的技术结论。

1. 数据与视图的关系

A01、A02；用输入框与摘要、日期范围、多端布局验证。

候选路线可能收益必须验证的代价
组件即字段普通输入配置集中、创建成本低。需验证无视图数据、多视图与多字段组件是否引入例外或重复定义。
数据与视图完全分离身份与职责明确，数据可独立复用。需验证绑定配置量、字段与视图同步维护、设计器编辑成本。
语义分离、配置一体化允许工具用一次操作生成数据与视图。需证明转换确定，能定位诊断，且不会隐含一对一限制。

收敛依据：比较数据复用、多字段绑定、跨端呈现和维护成本；用同一组样例统计配置量与例外数量，不先固定 Field / DataNode / ViewNode。

2. 表达式抽象

A03；同一条件用于显隐与必填，集合汇总及复杂领域计算。

候选路线可能收益必须验证的代价
受限字符串表达式书写紧凑、适合手工编辑。需要明确语法、类型、错误定位、解析与跨端求值契约。
结构化 AST结构显式，便于结构化编辑与分析。需要验证手写成本、协议体积与纯函数扩展方式。
表达式 + 注册纯函数可复用领域计算，同时保持通用纯函数规模。函数需声明签名、依赖和版本；检查不同端的实现一致性。

收敛依据：字符串与 AST 是表示选择，注册纯函数是扩展选择，二者可以组合。禁止用求值实现的名称直接推导新的用户抽象；复用策略单独比较内嵌、命名引用与参数化。

3. 校验能力

A04；条件必填、日期范围、集合唯一性、外部资格校验。

候选路线可能收益必须验证的代价
JSON Schema 为主 + 自定义 Keyword力求将约束集中在同一数据契约中。待验证 Keyword 的跨端实现、依赖声明、诊断及治理成本。
JSON Schema 基础约束 + 独立动态约束分别处理基础数据契约与表单动态业务要求。需要规定重叠约束如何组合、条件语义和统一错误协议。
统一自定义 Validation DSL可以统一组织业务规则的表达体验。需要评估自行维护类型、基础校验、工具及跨端执行的成本。

收敛依据：按协议复杂度、跨端一致性、静态分析、配置体验、扩展成本逐项比较。先建立约束分类，再做同场景样例和执行验证；本文没有选定路线，也未限定具体标准支持子集。

4. 联动行为

A03、A05、A06、A07；国家变化清空城市与重新查询。

候选路线可能收益必须验证的代价
以事件规则统一联动触发和操作直观，可覆盖主动赋值。需检查持续派生、重复触发、相互写入、循环与初始化行为。
派生、主动操作与资源分别声明可区分持续关系、一次性修改与异步生命周期。需验证概念数量和三者组合时的配置成本。
少量高频声明 + 受限组合规则常见联动可使用简化配置，复杂场景组合表达。需证明简化展开不会新增隐式行为或产生不同执行语义。

收敛依据：明确变化来源、有效变化、初次加载、同值赋值及资源结果是否触发。查询可以按依赖重新执行，提交等业务命令需要独立判断；不以增加通用工作流解决表单局部问题。

5. 引用与作用域

A02 至 A06；嵌套被保人、成员移动、根字段引用和集合聚合。

候选路线可能收益必须验证的代价
路径为主数据地址可读，适合直观绑定。需处理重命名、数组下标漂移、转义和结构变更。
稳定定义标识为主可使引用独立于显示名称或布局位置。需补充数组实例定位、引用可读性及数据地址映射。
稳定标识 + 显式相对作用域分别描述定义目标与当前实例上下文。需验证语法和配置成本，禁止产生隐式或歧义的作用域跳转。

收敛依据：用当前项、父级、根数据、集合聚合及按业务键查找验证；区分定义身份与运行时实例身份。跨行查找的键冲突、未命中和删除行为需要明确。

6. 配置复杂度控制

全部能力；用简单录入与复杂保险表单对照验证。

候选路线可能收益必须验证的代价
单一规范协议减少表示层和转换维护。需检查普通字段、简单显隐与校验是否承担过多配置成本。
简化配置 + 规范化协议常见场景可缩短配置，复杂场景保留完整语义。必须规定确定展开、错误来源映射、版本和工具编辑行为。
核心协议 + 受控扩展可把特殊物料与领域能力交给明确契约。需防止业务状态、依赖或跨端语义藏进不透明扩展。

收敛依据：划分原生、扩展和不支持的能力。双表示若不能确定转换，则不成立；是否能从规范协议还原简化配置要独立决定，不能默认承诺无损往返。

每项取舍的决策记录

统一记录关联能力、场景、候选方案、比较结果、选择理由、未解决问题和状态。状态使用 Proposed / Accepted / Rejected / Superseded；结论改变时保留替代关系。

06

贯穿场景：国家、城市与邮政编码

业务目标：用户修改国家后，清空城市，重新查询城市选项，并按新国家调整邮政编码校验。以下仅表达业务语义，不是最终协议，也不预设执行算法。

维度需要表达的内容必须讨论的边界
变化与操作国家有效变化时清空城市。初始化回填是否算变化？同值赋值是否触发？批量国家与城市回填的优先级是什么？
外部依赖城市选项查询使用当前国家作为参数。国家为空时是否查询？请求失败如何呈现？此前选项是否仍可使用？
动态约束邮政编码合法性依据当前国家决定。旧错误何时失效？空国家如何处理？隐藏字段是否参与校验？
结果接受城市选项只能关联当前有效的请求输入。先选国家 A 再选 B，A 的晚到结果不能成为 B 的有效选项。
提交边界提交时城市应属于当前国家，邮政编码满足适用约束。远程状态未完成是否允许提交？后端如何保持权威校验？
候选抽象

Reference 表达字段关联；Expression 表达条件和参数；Event / Command 表达清空意图；Constraint 表达合法性；Resource 表达查询依赖。这里验证覆盖能力，不据此确定对象目录。

实现职责

L2 检查引用并分析依赖；L3 管理状态、事务、校验与异步结果接受；L4 呈现状态和操作入口；Capability 执行实际请求。

需要决策的规则与必须实现的算法分开记录。例如，清空是否适用于草稿回填属于业务语义；请求版本检查采用何种内部结构属于 Runtime 实现。

07

复杂场景验证与可实现性门槛

场景验证能力与抽象通过条件
普通录入 + 输入与摘要A01 / A02；数据与视图关系简单配置成本可接受，一处数据被多处消费时无重复权威值。
日期范围 + 条件校验A02 / A03 / A04；多字段组件及错误定位清晰绑定多个数据目标，约束无需依赖 Renderer 才成立。
动态被保人列表 + 嵌套地址A01 / A03 / A04 / A05；引用和作用域增删、移动后引用正确，错误和异步结果不错误关联到其他成员。
国家城市联动 + 草稿回填A05 / A06 / A07；变化与初始化能区别用户修改与回填意图，晚到查询结果不覆盖当前有效状态。
报价 + 用户确认 + 提交A03 / A06 / A07；查询与业务操作查询依赖和确认操作分离，依赖变化后的报价有效性及提交规则明确。
Web / Flutter 对照全部；规范语义和扩展同一上下文及共享规则满足一致语义；显式选定的端、地区、产品策略允许行为差异，并分别验证。

反向检查 L2 / L3 / L4

  • 引用和依赖是否可分析？无法静态分析的部分，是否具有显式依赖契约及受限范围？
  • 持续计算、一次性赋值、异步结果与提交操作是否可区分，而无需猜测业务意图？
  • 写入冲突、循环、失效结果和非法配置能否定位到原始配置项？
  • 简化表示能否确定展开？相同输入能否得到相同规范语义？
  • 主要操作是否可避免无条件全量扫描？性能要求需要通过代表性场景验证，不能仅凭抽象判断。
  • 跨端纯计算、空值、约束、错误及扩展契约是否能形成一致的验证样例？

此阶段只需要概念样例、依赖推演和最小可实现性验证。完整 Store、调度器与渲染适配的实现仍在各层详细设计中展开。

08

复杂场景带来的取舍建议与待明确项

新增需求已明确：多端视图与行为允许差异，定义需要分层、解耦复用；生日校验依赖出行日期及国家地区计算规则；多级联动可能影响表单内部与外部。以下设计选择为 Proposed，不自动转为已接受方案。

8.1 多端差异：组合复用，而非整表复制或深层继承

建议将数据契约、业务规则、交互行为和视图片段分别复用，再通过明确的场景配置组合。它们是复用职责，不预设四个顶层 JSON 字段。Web 与 Flutter 可以选用不同布局、校验触发时机、选择顺序和操作入口，也可以有显式的渠道业务策略。

复用内容共享部分允许差异
数据契约字段含义、数据结构及提交映射场景附加字段、版本化映射；必须明确，不能仅由布局改变数据含义
业务规则通用约束、计算与领域函数国家地区、产品、渠道等显式策略
交互行为可复用操作与联动片段触发时机、步骤、确认方式及宿主操作
视图定义语义绑定、通用片段组件、布局、展示方式与端专属交互

权衡：整表复制易起步，但共享规则容易漂移；深层继承节省重复，却使覆盖来源和执行结果难以追踪。建议采用具名片段组合及显式替换规则：约束按标识替换、操作列表明确追加或替换，写入目标冲突报错，不使用任意深合并决定语义。

L2 将选定的片段和策略解析为具体定义，并保留来源诊断。若运行中允许切换地区或产品，动态选择必须成为显式依赖，规定状态重算与资源失效。跨端一致性指相同上下文和共享规则具有相同语义，不要求不同场景的行为和结果完全相同。

8.2 复杂校验：基础契约 + 上下文计算 + 动态约束 + 外部验证

建议优先采用 JSON Schema 基础约束与独立动态约束组合的路线，将复杂领域计算放在可版本化、可测试的纯函数中，只有依赖外部权威信息时才调用 Capability。先不通过不断增加 Keyword 承载全部交互，也不另造完整基础校验语言。

业务语义示例 / 不是最终协议
生日 + 出行日期 + 明确的地区策略 + 规则版本
    → 出行时的资格年龄 / 有效计算结果
    → 产品年龄范围约束
    → 生日字段错误或成员级错误
    → 资格状态与报价可用性

“地区”不应等同于界面语言；出生地、居住地、目的地、产品销售地区可能含义不同。具体年龄计算不在本文预设。必须明确资格年龄的用途、参考日期、日历与时区、临界日、闰日及规则生效版本。

权衡：分开基础与动态约束会增加组合契约，但可以显式呈现跨字段依赖和错误归属。领域函数需声明参数、返回值、纯计算约束及版本；不同端使用同一组业务样例验证。缺失或非法输入使计算结果不可用，下游约束标记阻塞或未就绪，不应将其伪装成合法值或继续发报价请求。

基础规则与动态规则默认累积适用；同一约束的替换需要明确标识和策略。同步与异步校验统一结果状态、错误定位及提交门槛，避免同一基础约束在两处重复定义。

8.3 多级联动：纯派生、内部操作与外部效果分开

类型示例建议执行语义
持续派生出行日期影响资格年龄，资格年龄影响校验显式依赖，纯计算；不因校验消息变化触发下一层写入
内部主动操作国家变化清空城市，城市变化清空区县声明触发来源、条件和写入目标；本地事务内稳定后再对外通知
外部查询城市选项、报价、外部资格验证稳定快照作为参数；按相关输入与作用域检查结果是否仍适用
外部业务操作更新宿主订单、保存、通知其他模块显式 Capability 或宿主事件契约；说明确认、幂等、失败与补偿归属

权衡：统一事件链容易配置主动操作，但难以分清持续计算、重复执行和外部副作用。建议采用受限组合：声明触发、条件、操作及结果接受方式，暂不加入任意循环、分支脚本与跨系统事务。

多级联动允许继续传播，但必须分析循环、重复触发及多写入者冲突。外部返回结果经受控命令进入新事务，且检查相关输入、目标修改和作用域身份；不以整个表单任意变化都丢弃结果，也不允许外部直接修改内部 Store。若业务要求长期等待、人工审批或跨系统恢复，应交给宿主编排。

8.5 场景细化检查项（不阻塞 L1 设计）

  1. 端差异：实际有哪些端？举一个视图不同、一个操作顺序不同、一个业务规则不同的实例。规则差异源于平台本身还是产品、渠道、权限？
  2. 生日校验：出行日期影响的是允许填写的生日范围，还是由生日计算年龄后判断资格，或两者都有？规则选用哪一种国家地区，有哪些具体边界样例及规则来源？
  3. 外部联动：影响外部是单向通知、查询结果带回、修改宿主状态、更新另一张表单，还是有不可逆业务操作？是否等待外部成功才能继续？
  4. 触发和覆盖：用户输入、草稿回填、宿主批量赋值是否走相同联动？自动结果能否覆盖用户已经修改的值？
  5. 发布与恢复：填写过程中地区或产品能否切换？草稿恢复采用原规则版本还是当前版本？

优先拿一条真实完整链路验证：出行日期 → 地区年龄计算 → 生日资格校验 → 报价 → 宿主状态更新。标出每个节点的输入、输出、来源、是否可覆盖及失败后的要求，再用 Web 与 Flutter 的差异版本做对照。
