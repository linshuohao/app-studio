03

E1 · 统一 Expression 形式

决策：采用结构化 JSON AST 作为 L1 规范表示，后续设计器可以提供条件构建器；字符串语法若有价值，只能作为可选 Authoring 输入并转换为规范 AST。 本轮原则确认

备选方案优势主要风险判断
A · 字符串 DSL写起来短解析器、沙箱、静态检查、跨语言兼容成本高不作为核心规范
B · 自定义 JSON AST结构清晰、易类型检查、可视化编辑友好原始 JSON 较冗长采用
C · JsonLogic 等现成 DSL部分生态可复用运算符、类型、Missing/错误、Scope 与当前需求仍需适配参考而非直接等同于协议

核心 AST 基元：字面量 / 引用 / 纯函数调用

JSON · 示意 AST；规范化 Reference 形式沿用第一组
{
  "op": "and",
  "args": [
    { "op": "gte", "args": [ { "ref": "/age" }, 18 ] },
    { "op": "eq", "args": [ { "ref": "/country" }, "JP" ] }
  ]
}

静态 JSON 对象与表达式对象绝不能通过“是否恰好拥有 op 字段”做全局猜测。这是 E6 Dynamic Slot 的根本动机。

未冻结：字面量对象的包装形式、所有 AST 节点标签、Schema 类型定义与 Source Location 诊断信息。
04

E2 · 类型、工作值与错误传播

决策：运算符遵循严格类型语义；Data 引用通过 Schema/Codec 做类型化读取。表单的唯一可变权威数据是 Work Data；读取失败不使用上一次合法值。 本轮原则确认

Typed Read · From single Work Data
Form Working Data唯一可变的数据源 · 可暂时不满足目标契约
↓
Schema / Codec Typed Read读取当前工作值并尝试按目标类型解析
↓
Success(value)提供明确类型的当前值
Failure(error)向上传播读取／类型错误
工作值或数据情况读取语义计算与校验
age = "20"，Schema integer可解析为数值 20继续数值比较
age = "abc"，Schema integerParse Failure相关表达式失败，不静默判 false
age = "12."，严格整数/小数输入规则不接受Parse Failure与其他无效输入统一；没有 Incomplete
age 属性不存在Missing由存在性和规则适用策略处理
age = null明确 JSON null依 Schema 和纯函数签名判断

哪些语义仍然要细化？

  • Missing 是独立引用结果还是求值错误的一类；无论采用哪种表示都不得等同于数值 0、字符串空值或布尔 false。
  • 逻辑运算符的短路顺序及错误传播（例如 false && Failed 是否产生 false）需要明文规定。
  • 空值、零、空字符串、空数组等不得依赖 JavaScript 真值性隐式转换。
  • 当类型不可用时，派生表达式、Constraint 和 Resource 各自如何处理由消费者语义决定；不能把错误统一“吞掉”。
避免重开第一组 D2

不重新引入双 Store、通用 Input Buffer 或 Incomplete 解析态。不同终端控件的临时焦点、选区和输入法状态是本地 UI 状态，不是第二个业务数据源。

E3 · Pure Function 的内置范围与扩展

决策：小型通用纯函数集满足高频条件和简单计算；复杂、领域性强的算法由已注册、纯函数、版本化的 Pure Function 承载。 本轮原则确认

类别候选能力阶段性判断
比较eq / ne / gt / gte / lt / lte基础候选
逻辑and / or / not基础候选
存在与空值exists / isNull / isEmpty基础候选，具体定义待定
算术add / sub / mul / div基础候选
条件if基础候选
集合count / some / every / sum限量提供，详见 E5
字符串／日期／显式转换length / contains / compareDate / toNumber 等按真实场景分批进入，不追求全量
JSON · 复杂领域算法收敛至Pure Function
{
  "call": "calendar.ageAtDate",
  "version": "1",
  "args": [
    { "ref": "/birthDate" },
    { "ref": "/referenceDate" },
    { "ref": { "source": "context", "path": "/agePolicy" } }
  ]
}
TypeScript · 概念契约，非最终接口
interface PureFunction<I extends readonly unknown[], O> {
  id: string;
  version: string;
  inputTypes: readonly ValueType[];
  outputType: ValueType;
  evaluate(args: I): O;
  // 能力声明还需明确可移植性和成本约束
}
  • 必须是纯计算：不得在求值中调用网络、执行不可控副作用或直接写 Form Data。
  • 确定性的上下文通过显式参数传入，不能随意读取当前时间、Locale 或宿主全局变量。
  • 跨端实现需要同一签名、版本和黄金测试；未实现的纯函数应在 Preparation 或目标平台兼容性检查中被明确拒绝。
  • Pure Function 封装不能绕过成本预算和治理，应有性能约定、测试和诊断。
待细化：内置纯函数的精确定义、日期／金额精度、Pure Function Registry 声明、版本匹配、成本标注。

E4 · 命名表达式与复用

决策：小表达式默认内联；较复杂或反复使用的逻辑用可选 Named Expression；表达式之间允许引用但不允许循环。 本轮原则确认

JSON · 命名复用的候选表示
{
  "expressions": {
    "ageAtDeparture": {
      "call": "calendar.ageAtDate",
      "version": "1",
      "args": [
        { "ref": "/birthDate" },
        { "ref": "/departureDate" },
        { "ref": { "source": "context", "path": "/agePolicy" } }
      ]
    },
    "isMinor": {
      "op": "lt",
      "args": [ { "use": "ageAtDeparture" }, 18 ]
    }
  }
}
Named Expression · DAG instead of copy/paste
ageAtDeparture纯领域计算
↓
isMinor引用已有表达式
↙↘
View.visible消费布尔结果
Constraint.assert消费派生结果或原始年龄
  • 命名表达式不是自动回写 Data 的计算字段。
  • L2 构建共享的表达式依赖关系，不应将 use 递归展开为无数重复 AST。
  • 引用的作用域应在定义时明确：同一表达式在不同数组项中求值，属于不同的 Scoped Evaluation。
  • V1 不支持协议内自定义带参数函数、递归、任意循环或高阶函数。
待细化：作用域内名称可见性、覆盖与冲突策略、缓存键和失效依赖、是否允许跨 Form Definition 复用 Named Expression。

E5 · 集合计算与词法 Scope

决策方向：不引入完整 map/filter/reduce 数据编程语言；针对表单常用的数量、存在性、全称判断、求和提供受限集合纯函数，并复用第一组定义的词法 Scope。 方向认可

方案覆盖能力代价阶段性结论
只有 count 等最少集合纯函数集合长度等简单计算计算单项结果频繁需要专有纯函数能力偏弱
有限聚合 + 局部 Scopecount/some/every/sum 及 item 局部读取引入受控迭代绑定推荐
完整函数式集合语言map/filter/reduce/flatMap 等接近通用编程 DSL，类型与成本复杂V1 不采用
JSON · 数组中逐项计算 price × quantity 再求和
{
  "op": "sum",
  "collection": { "ref": "/items" },
  "as": "item",
  "select": {
    "op": "mul",
    "args": [
      { "ref": { "scope": "item", "path": "/price" } },
      { "ref": { "scope": "item", "path": "/quantity" } }
    ]
  }
}

这里的 as: item 是求值期间的词法绑定，不是新的业务数据源，也不等于 Repeater 的运行时组件实例。

必须继续确认的边界

  • 空集合下 sum、every、some 的返回规则。
  • 部分数组项类型解析失败时，是整项失败、跳过，还是产生带位置的诊断；不允许隐式跳过导致错误结果。
  • 数组深度、集合规模、嵌套迭代复杂度的上限；filter 是否真的值得作为 V1 原生能力。
  • 依赖提取需覆盖集合结构及其元素属性，且在数组项移动、增删时能够正确失效。
当前边界

有限聚合是一种 Expression 能力，不是通用表格查询语言。复杂多层分组、排序、递归统计优先用可测试的Pure Function 解决。

E6 · Expression Slot 与静态/动态识别

决策：Expression 只允许出现于协议或 Material Manifest 明确声明的动态槽位；对于同时允许静态值和表达式的属性，采用显式 $expr 标记。绝不对任意 JSON 对象自动猜测。 本轮原则确认

Static Slot只接受静态值：kind、widget、布局类别等。
Expression-only Slot本身就接受 Expression：constraint.assert、when 等。
Dynamic Value Slot接受静态值或动态表达式：visible、disabled、已声明的动态 Props。
JSON · 静态槽位值
{
  "kind": "section",
  "visible": true
}
JSON · 动态值槽位：显式表达式
{
  "kind": "section",
  "visible": {
    "$expr": {
      "op": "eq",
      "args": [ { "ref": "/accountType" }, "enterprise" ]
    }
  }
}
JSON · 静态配置对象，即使存在 op 也不自动当表达式
{
  "kind": "field",
  "props": {
    "filter": { "op": "eq", "args": ["name", "Alice"] }
  }
}

候选槽位权限矩阵

所属属性类型动态程度理由

Data 初始化默认值或上下文初始化参数受控动态，另行声明与运行时初始化策略对齐

关于对象值歧义

在允许任意 JSON 对象作为静态值的动态槽位，若静态对象本身含 $expr 键，需要明确定义显式字面量包装／转义形式。这属于必补细节，不能依赖对象属性名猜测。

E7 · 复杂度收拢与预算

决策：复杂逻辑按“内联 → 命名表达式 → Pure Function → 外部 Capability”逐级收拢；采用静态和运行时的多维成本预算，而不是只限制 AST 深度。 本轮原则确认

Expression abstraction ladder
Inline Expression条件少、规模小，直接使用
↓ 逻辑复用 / 结构增长
Named Expression共享局部计算关系，形成可分析的 DAG
↓ 领域算法复杂
Pure Registered Pure Function版本化、强类型、测试覆盖的复杂计算
↓ 需要真实 I/O / 权威判断
Resource / Validation Capability进入明确的外部生命周期，不在 Expression 内偷偷请求
控制维度L2 / 发布前检查L3 / 运行时保护
AST 深度与节点数限制单表达式大小不重复解析 AST
命名表达式图环检测、可达图规模、最大引用链按 Scope / 快照复用；不无限展开
Pure Function 合法性注册、版本、输入输出类型、成本声明对计算失败与超预算执行诊断
集合和嵌套聚合限制迭代层数与静态估算成本限制实际集合规模和累计运算成本
全表单总体成本估计规则数量、依赖度与最坏情况约束高频触发的累计计算量
  • 不支持递归表达式、任意循环和用户定义的通用高阶函数。
  • 把长表达式拆成十个命名表达式，不能绕过整个可达依赖图的限制。
  • Pure Function 也会消耗 CPU；不能通过“藏进代码”绕过治理。同步计算是否能够真正中断，需要特定执行隔离机制，不能只靠同步调用外层的超时检查。
  • 超限必须产生确定的诊断或错误，不静默截断集合后返回不完整结果。
待细化：阈值（深度／节点数／图大小）、Pure Function 成本分级、是否启用隔离执行及性能基准。
10

C1 · Constraint 的最小协议

既定基线：结构和基础约束复用 JSON Schema；复杂同步约束声明为独立 Constraint；高频规则未来可以版本化资产化。 已确认

本轮方向：复杂同步约束优先采用统一 when + assert + target 语义，避免按 field/cross-field/collection/form 创建大量互相重叠的规则子类型。异步权威校验采用独立生命周期而非伪装为纯 Expression。 方向认可

备选方案优点问题推荐
统一同步断言可复用 Expression/Reference/Scope；静态分析直接需要补充错误归属、异步策略采用为基础
按字段／集合／跨字段细分类型对某些场景易读分类相互重叠，执行分支多不作为核心分类
异步同一断言表达式表面统一破坏纯求值和同步性边界不采用
JSON · 独立复杂约束的示意：字段归属不等于全部依赖
{

与 Behavior 的边界

Constraint 只报告合法性，不修改 Work Data。Behavior 的 Reaction / Command 负责显式数据变更。二者可以共享 Expression 语言，但不共享副作用语义。

C2 · 校验生命周期与错误归属

方向：把“当前数据是否符合约束”与“什么时候执行／展示错误”分开设计；前者属于 Constraint 语义，后者由 Validation Policy 与 Runtime 负责。 方向认可

议题当前原则保留讨论
校验时机不强制每条规则重复定义 change/blur/submit默认策略和覆盖层级
错误归属使用数据引用／Scope 定位，不绑定某一 ViewNode多目标及汇总错误规范
字段显隐不因未渲染或隐藏就隐式取消约束约束适用条件与用户反馈
编辑态允许暂时无效工作数据，不因此拒绝普通编辑提交门禁与分步校验
异步校验Pending、Valid、Invalid、Execution Error 是任务状态超时、过期、取消、提交策略
错误显示PC 字段下错误／移动卡片汇总由 View 负责跨视图错误定位策略

C3 · 规则资产与跨端一致性

决策：简单约束留在 Data Schema，复杂一次性约束内联在当前表单；跨表单高频复用时才将规则提取为带参数和版本的 Rule Asset。V1 只要求能声明和解析能力，暂不建设完整规则市场。 本轮原则确认

复用层级推荐做法主要价值
标准数据约束JSON Schema标准生态和简单配置

同表单复用计算Named Expression避免重复 DSL
通用领域计算算法Versioned Pure Function算法复用、跨端一致

跨端一致性的必要测试

  • 相同字段 Work Data、Context、Pure Function 版本和 Scope，应有相同 Expression 及 Constraint 结果。
  • 类型、日期、数字精度、字符串比较、逻辑短路、缺失值及错误传播都应形成规范测试向量。
  • 不同 Renderer 可以采用不同 UI 呈现和错误定位，但不能私自重新定义业务合法性。
待细化：规则资产版本锁定、参数契约、构建期解析、差异化跨端兼容策略。

与 View Interaction 边界

第二组最终结论

Expression 是一门受控、纯函数式的配置语言，而不是任意可执行 JSON。明确 Slot 管出现位置、Pure Function 管复杂算法、Named Expression 管复用、L2/L3 管静态和运行成本；Constraint 消费相同语言，却拥有独立的合法性语义。
