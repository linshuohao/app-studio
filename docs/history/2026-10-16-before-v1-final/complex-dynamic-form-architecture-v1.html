01

产品能力边界

我们建设的是复杂动态表单与数据录入引擎，不是通用页面搭建器、任意逻辑编排平台或完整 BPM 系统。所有原生能力都应服务于表单式数据交互。

能力范围处理方式原因
字段定义、数据绑定、布局分组引擎原生表单基础能力
条件显隐、必填、禁用引擎原生高频且容易标准化
跨字段计算、动态校验引擎原生复杂表单核心价值
嵌套对象、动态数组、重复区块引擎原生需要统一状态及身份管理
初始化、批量赋值、重置核心需明确生命周期契约D7 原则已确认；F1/F2 推荐静态补缺与最近初始化基准，精确 API/触发仍待细化
异步选项、远程查询、服务端校验Host / View Adapter（核心外）请求、缓存和重试归外部；Runtime 登记被动五态/有效性与 Readiness，精确接口待细化
分步骤表单View / Lifecycle 范围View 方向已定，F5 Readiness 已确认；Host 执行提交，步骤及接口细节仍待协议收敛
自定义复杂业务字段物料扩展隔离领域特殊性
报价、核保、审批宿主业务服务保留权威业务状态
任意页面搭建、营销动效、通用 BPM明确不在范围成本与核心目标不匹配
边界决策

仅为“表单式数据交互”提供完整执行语义。核心提供被保人录入、纯计算、同步条件联动及约束；异步报价预览由 Host / View Adapter 集成，审批、支付、生成保单等跨系统流程由宿主系统负责。

04

L1 · Definition：当前已确认的设计边界

L1 声明数据、视图、纯表达式、同步约束及 Command / Reaction；Host 集成约定保持明确边界。具体协议组织仍未定，当前结论与状态以 L1 决策台账 为准。

关注点当前边界
Data / View已定稿：共享 Data、多份独立 View Profile，可有不同树与交互路径。Profile 与平台目标分离。
Constraint已定稿：Schema 基础与原生约束 + Form Constraint 复杂约束 + 按需 Rule Asset；统一结果。
Expression第二组原则确认：JSON AST、严格类型读取、Pure Function、命名复用、受控 Slot 与多维预算；不另立 Computation DSL。
Behavior第三组：核心行为收敛为 Command + 同步 Reaction；派生不自动写回，约束只判合法性，外部请求归 Host。
引用与编辑第一轮已采用类型化 Reference、词法 Scope、Runtime ID 和受控 Binding；精确语法及迁移细则待细化；V7 已确认默认 Live Edit，额外隔离/撤销按未来明确需求另评审。
协议与复用AST 规范表示已确立；精确节点、目录与字段名、片段参数、可选作者简写仍待细化；当前采用单一逻辑 Definition、Profile entry / Named Template，不预设无限 Override。

一个 Data 可被多个 View 消费，一个复合控件可读写多个字段；UI 显隐与数据合法性分开，字段未挂载不自动取消约束。

下一步

第一轮决策已收敛，见 D1–D7。第二组 E1–E7 / C1–C3 已归档。第三组 B1–B8 与 Host 边界 已集成，第四组 V1–V7 已集成，第五组 F1–F6 已归档，第六组 统一协议方向 已归档，下一步为 Material Contract + Validation Metadata。

05

L2 · Preparation：定义预处理层

先不把它设计成完整编译器。它的核心职责是：把易编辑的 Form Definition 安全、稳定地转换成 Runtime 可直接消费的 Prepared Form。

5.1 服务对象

直接服务 Runtime、配置设计器、发布构建流程与测试工具。业务配置者主要消费它输出的诊断结果。

5.2 预处理流水线

第二组补充：Slot 与复杂度治理

L2 只在声明的 Expression/ValueSpec 位置识别表达式；ValueSpec 内递归显式 $expr，不逐深层 Prop 白名单，不按 op 对象形状猜测。Work Data、Schema default、外部原始 JSON 和结构字段不被扫描执行。检查 AST、类型、引用环与可达图成本；Named Expression 不无限展开。Literal 精确转义和具体阈值继续细化。L3 消费准备产物，执行实际规模与累计成本保护，不静默截断集合返回错误结果。

5.3 复杂度取舍

问题V1 方案暂不引入
解释 vs 预处理加载时准备一次每次联动重新解析配置
编译深度Normalizer + Analyzer + Indices完整代码生成与重型优化器
依赖关系预提取表达式依赖通用动态依赖语言
物料检查检查标识、版本和接口执行物料内部代码
循环检查检测纯计算环并报错默认支持固定点求解
产物缓存按版本与内容 Hash 缓存复杂编译集群

例如 500 个字段和 200 条表达式的表单，Runtime 应能根据预处理索引找到受影响节点，而不是字段每次变化都扫描整份配置。但性能收益必须实测。

边界：Preparation 不是第二套 Runtime

Prepared Form 可以包含数据定义、已准备表达式、Command/Reaction 描述、依赖索引与物料契约，但不能包含用户输入、焦点、错误状态、请求状态和当前会话。一个 Prepared Form 应允许多个表单实例安全复用。

06

L3 · Runtime：表单内部状态事务

Runtime 拥有唯一可写 Work Data，处理表单内部确定性修改、纯计算、同步约束与联动。第三组把 Resource Store、网络生命周期和通用外部动作移出核心；以下为模块职责，不冻结内部算法。

模块当前职责不承担
Data / Value工作态允许无效或暂不可解析；Typed Read 仅成功/失败，不能回退旧值第二个可写输入 Buffer 或 Incomplete 类型
Scope / Identity类型化引用、词法 Scope、稳定 Runtime ID 与数组实例数组下标永久身份、强制业务 __id
Expression受控 AST、Pure Function、命名 DAG、类型检查与成本保护I/O、任意脚本和自动写回
Command / Reaction受控数据修改、多引用 OR watch、纯 when、同步 then业务函数调用、异步 Reaction、通用事件总线
Validation / Readiness同步约束 + 已知外部义务/被动五态/Issues/依赖有效性；统一报告与输出准备发起远程校验、重试/超时或业务提交
Form Lifecycle / Editing Context实例能力和正交状态；F1/F2 初始化/Reset 推荐，F3 默认 Live、F6 不建统一流程状态机Host 持久化、提交流程及跨系统事务

6.1 修改与变化不是一一对应

Set/Replace、Patch、Remove、数组 Insert/Remove/Move、Batch 表达数据修改意图；字段名和最终 API 尚未冻结。一次替换对象可影响多个子引用，Diff 与去重属于 L2/L3。

6.2 Reaction 与纯派生分开

watch 中任意实际变化使规则成为候选；when 的读取依赖不自动加入 watch。then 只修改 Work Data。显隐、总价和合法性分别由 View Slot / Expression / Constraint 表达，不通过 Reaction 写入另一份状态。

6.3 顺序与稳定发布

同步顺序确定，同目标后写覆盖，不默认报错或要求 priority。跨轮级联顺序、相等性、循环、预算、回滚与候选状态算法留待 Runtime 契约。执行失败不发布半成品；业务 invalid 或 Parse Failure 不自动拒绝普通编辑。

6.4 外部数据与被动校验事实

Host 订阅稳定数据并管理外部请求，再用 Command 写回。Runtime 被动登记已知义务的 Unverified/Pending/Valid/Invalid/Error 及有效性，生成 Readiness；这是校验事实，不是请求执行器、Retry 或网络 Cache。具体接口与失效机制待细化，不恢复 Resource Store。

第三组依据

详见 职责交接 与 未冻结事项。Runtime 算法没有在 L1 冻结。

07

L4 · Renderer：MaterialNode / ScopeNode / TemplateUse

ViewNode 收敛为 MaterialNode、结构性 ScopeNode 与 TemplateUse。容器、布局和复合业务组件都是 Material；Material 通过 trigger/content 等 Slots 自主管理开闭、焦点、动画与 UI State，Slot 名称本身不自动赋予点击行为。

Profile 使用 entry；需要复用或独立引用时定义 Named View Template 并静态 $use，不再另建 root/targets/fragments 多套内容目录。模板参数显式接收 ScopeHandle，不隐式捕获外部局部变量；共享定义不共享组件实例和 UI State，也不复制业务数据。

Binding 只关联数据，默认端口与具名端口沿用同一模型；具体绑定字段名仍候选。children 建议作为 slots.default 的 Authoring 简写，同一节点不能同时给两者。Manifest 声明 Props 类型、Binding/Slot/Event 端口；Material Validation Metadata 的消费契约仍是明确缺口。

核心 view.present / view.dismiss 与独立 Presentation Spec 已移出。Interaction 仅保留 form.command、host.emit 的受限连接；普通字段修改走 Binding Adapter，不额外重复声明写入事件。跨树 UI 协作先用复合容器或 Host，不恢复核心 UI Action Engine。

默认 Live 与校验事实

所有 Profile 默认编辑唯一 Work Data；Profile 切换不自动初始化或重放修改。Material 消费当前值、同步结果和 Runtime 被动外部校验事实；如何向输入、对象摘要和列表提供 Validation Metadata 是本轮明确缺口，尚未冻结具体 Adapter API。

完整依据：ViewNode、组合验收缺口。

08

Material：容器、端口与校验元数据

Material 包括输入、展示、布局、Modal/Drawer/BottomSheet 等容器及复合业务物料。容器负责开闭、Portal、焦点与 UI State；不是核心 Presentation Mode。

契约当前方向剩余边界
Props按 Material Schema 校验递归 ValueSpec；显式 $expr 与 Literal 转义。Schema 包装、最终转义与类型推断。
Binding默认/具名 DataReference 端口，只关联数据；修改走 Command。端口值类型、复合变更与错误传播接口。
Slots容器声明基数；children 建议简写 slots.default，不允许重复提供。具体 Slots Schema、交付展开和平台适配。
Events按需类型化事件端口，仅 form.command / host.emit 受限映射。Payload/source:event 与捕获 Scope 的精确消费和权限。
Validation MetadataIssues 归 DataReference + Scope，与 UI 节点分离。输入物料、对象摘要、数组项汇总如何读取状态与 Issues，需优先补齐。

Named Template 静态复用结构，显式 ScopeHandle 参数；不共享组件实例或独立业务 Store。Host Services 可注入给物料内部远程需求，不在 L1 新建通用 Service/Action 模块。

09

Host / View Adapter：外部集成边界

保留章节锚点以兼容旧链接。第三组替代此前 Runtime 调用 Capability、管理 Resource 生命周期的建议：远程请求、Loading / Error / Retry / Cache、上传、提交及工作流均由 Host / View Adapter 管理。

能力责任流向
远程城市选项Host 订阅 country → 外部查询与选项状态 → View 显示 → 用户选择经 Command 写回。
地址自动填充Host 验证请求结果仍适用 → 通过单个对象或复合 Command 更新 → Runtime 同步结算。
用户名唯一性Definition/Host 登记义务 → Host 执行并上报五态 → Runtime 校验结论有效性、汇总 Readiness → 多 View 消费状态/诊断；正式接口未定。
上传与提交Host 管理业务成功、失败和持久化；不当作表单内部 Command。
复杂纯计算注册、版本化Pure Function，可有跨端实现；不包含网络副作用。

Command 只描述 Form Data 修改，不提供业务 Command 执行器；Host 不能绕过 Command 写 Store。第五组已确认 Runtime 登记校验义务、被动状态和 Issues/有效性，生成 Readiness；精确 API 未冻结。Ready 不等于 Host 提交许可，Host 仍自行执行请求、权限与业务检查。

第六组明确三条 Host 路径：外部 Constraint 义务 / Validator，Material 事件 host.emit，物料内部注入 Host Services。必要能力缺失需诊断，不建设通用宿主工作流。详见 EXT-1 / EXT-2、VAL-EXT。

10

Tooling：设计器、调试器、发布与治理

先解决定义和运行时语义，再投入复杂拖拽设计器。第一阶段优先实现 Definition Editor + Preview + Runtime Devtools，降低验证成本。

阶段工具直接价值
阶段一Definition Editor、Preview、Diagnostics快速验证协议与运行时
阶段二Rule Builder、Runtime Trace降低逻辑配置与调试成本
阶段三可视化 Form Studio降低业务配置门槛
阶段四Release Console、Material Manager规模化交付与治理

10.1 版本从第一版开始治理

版本对象意义
Definition Revision具体表单业务定义的修订
Definition Format Version协议格式与语义版本
Runtime Compatibility该表单需要的执行能力
Material Versions所依赖的物料及其版本
Data Contract Version草稿与已保存数据的结构版本

发布表单应形成不可变 Release Artifact，默认让运行中的会话固定已发布版本，避免中途变更计算语义。配置迁移与历史草稿数据迁移应分开处理。

10.2 工程质量保障

静态质量

引用检查、类型校验、物料能力验证、潜在写入告警与依赖环分析，不默认拒绝合理同目标顺序覆盖。

运行时质量

事务一致性、同步级联、动态数组、循环与错误隔离；远程竞态在 Host 集成测试验证。

跨端契约

同一数据、上下文和共享规则产生一致语义；不同 Profile 的交互路径与 staged 模式分别验证。

发布与可观测性

不可变版本、灰度回滚、因果链 Trace、性能指标和脱敏日志。

11

完整交互：内部稳定修改与 Host 请求分开

案例仍用投保录入验证复杂表单，但外部报价并非核心 Resource。业务流程由 Host 自主组织。

职责时序示意，非调度算法
用户修改数据 → View 发出 Command
Runtime → 当前 Work Data + 同步 Reaction 结算
Runtime → 纯计算与同步 Constraint → 稳定状态 / 诊断
View / Host ← 订阅稳定结果

Host → 判断是否需要报价 → 发起并管理请求
Host → 检查结果仍适用 → 外部报价状态供 View 展示
Host → 确需更新业务字段时发出 Command
Runtime → 新一轮内部同步结算

Definition / Host → 注册必需校验义务
Host → 执行并上报外部校验状态
Runtime → 检查当前有效性 → 统一 Report / Readiness / Output（精确 API 待定）
Host → 核对当前报告/输出及业务条件 → 自主提交

执行失败不发布部分成功；业务不合法仍可作为工作态。网络失败不是内部同步事务回滚，Host 负责请求及业务恢复。内部字段值和外部候选/报价状态不混为一份 Work Data。

12

六大设计方向映射到各层

六个方向不是六个纵向层级，而是贯穿各层的设计与评审维度。

设计方向主要涉及层次核心问题
协议灵活度与复杂度Definition + Preparation简单配置简单，复杂场景可组合
逻辑编排与运行时Runtime状态如何稳定计算、提交与恢复
跨端一致性Definition + Runtime + Renderer哪些规则共享，哪些视图与行为按显式策略差异化
物料与扩展性Material + Renderer + Host Integration业务扩展不侵入核心
版本兼容与演进Definition + Preparation + Tooling历史配置、数据与依赖长期可用
工程治理与质量所有层每个关键语义可验证、可追踪

必须警惕的跨层破坏

协议任意 JS

可能破坏跨端语义和静态分析能力。

物料直接写 Store

可能绕过事务与状态一致性。

索引不带版本

可能破坏缓存、发布及回滚正确性。

Renderer 自算业务

导致各端规则漂移与权威数据分裂。

13

架构决策与 L1 主台账

总体产品定位与四层架构保持；横向集成按第三组收缩为Pure Function / Material 与核心外 Host 边界。L1 决策状态集中维护在 决策归档的唯一主台账，本文不另维护一份可能漂移的详细 ADR 状态表。

台账区分已定稿、原则确定、待讨论和已修正/不沿用。已定稿指职责与方向，不代表协议字段、AST 和运行策略已经冻结。

L2 / L3 / L4 的内部实现、数据结构及接口草图仍为候选，不因 L1 方向确定而自动接受。后续若改变已定方向，应记录前提、替代方案与历史变更。

14

逐层设计路线与当前讨论入口

当前聚焦 L1，前六组架构方向已阶段归档。按 L1 ADR 路线图 第六组已阶段归档，优先 Material Contract + Validation Metadata，再定稿 Schema；外部 I/O 交给 Host。以下为跨层推进顺序，与 L1 内部 ADR 不是同一层次。

阶段内容
01 · L1前六组已阶段归档；补齐 Material Validation Metadata，再交付最终 Schema；保留细节后续细化。
02 · Runtime 状态在 L1 契约约束下设计工作数据、稳定身份、快照与编辑上下文。
03 · Runtime 执行依赖计算、数据 Command、同步 Reaction、事务与同步约束；反向验证 L1。
04 · Preparation根据执行需求确定规范化、静态诊断、依赖索引与准备产物。
05 · Renderer / 扩展实现 Profile、平台与物料，衔接 Host Adapter；不引入核心 Capability 引擎。
06 · 治理兼容、迁移、作者体验、测试矩阵、发布及观测。

定义与执行契约迭代验证，语义讨论不等于提前实现全部 Runtime。每项 ADR 使用需求 → 候选 → 配置示例 → 覆盖与成本 → 失败路径 → 决策的模板，并使用 固定用例 S1–S6 检查。

第六组已阶段归档；下一步补齐 Material Contract + Validation Metadata，再定稿 Schema / 类型 / L2 契约与 Profile Bundle，随后 L3 专项。F1/F2、P6 与精确接口仍保留推荐/候选状态。
