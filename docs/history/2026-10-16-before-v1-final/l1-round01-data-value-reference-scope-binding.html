01

阅读说明与结论边界

第一组（Data / Value / Reference / Scope / Binding）无需再进行顶层方案投票，可以作为 L1 的阶段性设计基线。“方案已采用”不等于“JSON 语法及边界行为已经冻结”。

6主要方案按建议采纳（D1–D6）
1初始化原则采用（D7）
5重点待细化接口组
本轮采用 明确采用的架构方案
原则确定 明确方向，范围仍需补充
待细化 后续协议或执行契约尚未确定

本文是对当前会话已讨论内容的决策归档，不是将候选 JSON 直接提升为正式规范。涉及类型、字段名、纯函数和命令的代码示例主要用于表达能力与边界，后续 L1 协议设计可调整其具体语法。

已确认的上层约束

仍采用四层总架构：L1 Definition → L2 Preparation → L3 Runtime → L4 Renderer。Data 与多份 Views 独立；基础数据约束采用 JSON Schema，复杂约束独立建模，未来可选规则资产；Runtime 维护表单业务工作数据的唯一权威状态。

03

D1 · Data Schema：标准优先、最小扩展

决定 L1 如何描述目标数据的形状及基本契约本轮采用

A · 自定义 DSL

字段定义可以非常贴近配置器，但类型系统、递归引用、组合 Schema 和基础验证都需要大量自建。

B · 原生 JSON Schema

兼容性最好，但对领域特定的数据语义与编辑交互支持不足。

C · JSON Schema + 有界扩展

采用。保留标准数据结构；仅在真实场景要求统一的特殊语义时引入扩展。

核心规则：Data 定义结构化数据的目标数据契约，而不是 UI 控件配置。date 是数据语义，DatePicker 是视图物料；两者不能混用。

JSON · 设计示意，非冻结语法
{
  "data": {
    "schema": {
      "$schema": "https://json-schema.org/draft/2020-12/schema",
      "type": "object",
      "properties": {
        "name": {
          "type": "string"
        },
        "contacts": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": {
              "name": {
                "type": "string"
              },
              "phone": {
                "type": "string"
              }
            }
          }
        }
      }
    }
  }
}
决定理由与边界

JSON Schema 的 default 不会自动填充缺失属性，format 的验证语义也需明确。数据类型、固定范围、原生条件约束优先用 JSON Schema；复杂跨字段/计算型 Constraint 另行建模。

推迟到后续的细节 待细化

  • 是否通过独立的 data.annotations 表达领域元数据，还是使用有界的自定义 Schema 词汇；
  • Date / Decimal / Money 等类型的规范表示及跨端一致性；
  • Schema required 与工作数据缺失、编辑过程的关系。

D2 · Value：唯一权威 Work Data

这一项经过讨论明确修订，取消通用输入缓冲和 Incomplete 类型本轮采用

Runtime 只有一份可写入的权威 Form Working Data。输入中间态可以存在于这份工作数据中；解析后的类型化结果只是一种确定性视图，而不是第二套独立可变数据。

D2 核心模型
Form Working Data唯一权威的可变业务工作状态
↓
Type Parse / Codec从当前工作值推导类型化结果；只允许 Success / Failure
↓
Expression / Constraint使用有效的类型化输入或明确的解析失败
Host / Submit 边界Host 仅消费符合输入契约的当前值，外部请求与提交流程不属于 Runtime
TYPE MODEL · 概念代码 · 设计示意，非冻结语法
type ParseResult<T> =
  | { ok: true; value: T }
  | { ok: false; error?: ParseError }

// Missing 是属性/引用不存在，不是第三种 ParseResult。
// null 是显式值，其合法性取决于 Schema/类型契约。
// Validation invalid 是业务规则结果，不等于解析失败。
工作数据（示意）解析器结果下游行为
"12"Success(12)参与数值计算与业务约束
"12.5"Success(12.5)参与数值计算与业务约束
"12."取决于所选严格 Codec；可以失败失败时不得静默使用上次有效值
"abc"Failure下游得到不可用输入并诊断
属性不存在Missing（存在性语义）由 required 与读取规则处理
null显式 Null由目标类型和 Schema 决定是否合法

需要注意："12." 是否属于解析失败是 Codec 约定，不是 JavaScript 或 JSON Schema 的普遍结论；我们只确认不再额外引入 Incomplete 状态。

拒绝 · 全部立即强转

数值、日期输入可能丢失中间编辑形式，影响正常输入体验。

拒绝 · 第二个可变 Store

Buffer 与业务 Data 可能分叉，联动、校验以及 Host 读取时将出现多份业务真值。

采用 · 单一工作态

保留当前工作输入，所有联动基于同一版本的工作数据及可解析结果。

重要边界

输入法组合、焦点与选区等瞬时 DOM/UI 状态可以留在 Renderer；它们不是可参与业务联动的第二权威数据源。移动端确认/取消需要显式 Editing Context 语义，不能与输入中间态混为一谈；第五组维持默认 Live，额外隔离/撤销需求再评审，不预设通用子事务实现。

推迟到后续的细节 待细化

  • 具体 Codec 契约：严格数值解析、日期/金额表示、格式化与错误码；
  • 数字等字段的工作态稳定表示（始终字符串还是允许特定条件下规范化）；
  • Type Parse 失败如何传递到 Expression 与同步 Constraint；Host 如何获得当前可用值且不误用旧结果，消费接口仍待细化；
  • 从 Work Data 形成符合目标 Data Schema 的提交数据时，如何统一验证和序列化。
05

D3 · Reference：统一类型化寻址

用一套引用模型服务 View、Constraint、Expression 与同步 Command / Reaction本轮采用

采用：内部规范引用使用明确的数据来源（命名空间）与目标；当前 JSON 对象/数组位置采用 JSON Pointer；高频用例允许简写，由 L2 规范化；根路径简写始终从 Form Data Root 解析，局部数据必须显式指定 scope。

REFERENCE · 示意片段 · 设计示意，非冻结语法
// 简写：默认表单数据源
{ "bind": "/user/name" }

// 候选规范化形式
{ "bind": { "source": "data", "path": "/user/name" } }

// Host 显式提供的只读上下文，命名空间与目标仍是候选语法
{ "ref": { "source": "context", "path": "/locale" } }

// 远程城市选项不声明为引擎 resource 数据源。
// Host / View Adapter 管理请求、缓存、列表及加载状态；
// 用户选中的业务值通过 Command 写入 Form Data。
引用类型指向什么是否等同
Definition Reference定义结构中的节点，比如 Schema/视图模板不是实际数据值
Data Reference当前工作数据在某一位置的值路径会随数组重排而改变
Instance Identity某次会话中一个具体项或字段实例身份应在同一项重排时保持稳定

为什么不是只用字符串路径：它无法自然区分当前 Form Data、Host 显式提供的只读上下文以及某个作用域内的局部数据；混用不同路径方言会造成各模块各写一套解析器。

推迟到后续的细节 待细化

  • Reference 的精确判别联合类型、source 命名空间、是否允许引用定义节点；
  • 路径不存在、类型不匹配、被删除项的引用如何报告；
  • 引用表达式是否可指向整个对象/数组以及批量读取的权限与限制。

D4 · Scope：统一局部 ScopeBinder

第一组词法 Scope 方向沿用，第六组明确 from + as + mode（one/each）。作用域不只来自 View Repeat，Constraint/Reaction 规则入口也可建立局部绑定，L3 的实例身份仍只有一套。

根路径简写始终指向 Form Data Root，不因位于 Repeater 自动改变含义；局部数据显式指定 scope。JSON Pointer 的空字符串为根，"/" 是空名称属性，~1/~0 保持标准转义含义。

View ScopeNode、Constraint/Reaction 入口用同一 ScopeBinder：from + as + mode（one 默认、each 集合）。Binder 可以是一条有序词法链；from 必须是 DataReference，不由任意 Expression 动态生成，也不自动创建不存在的对象/数组。

one 绑定对象或确定位置，each 在 View 实例化子树，在规则中逐项适用。L2 维护词法绑定；L3 统一解析数据位置、稳定项身份和删除失效。View 与规则各自有词法帧，但不产生两套业务实例身份；不建全局 Scope Registry。

Data Reference 取得值，ScopeHandle 定位当前实例；数据相等不代表同一实例。事件环境包含受控 Payload（source:event）与捕获的 Scope；Handle 不是可直接发给外部服务的业务 ID。别名遮蔽、最终 Handle/替换语法仍待 Schema 与 L3 细化。

统一 Binder 的有序词法链（候选语法）
{
  "scope": [
    {
      "from": "/contacts",
      "as": "contact",
      "mode": "each"
    },
    {
      "from": {
        "source": "data",
        "scope": "contact",
        "path": "/phones"
      },
      "as": "phone",
      "mode": "each"
    }
  ]
}

View 在 ScopeNode 消费 each 来逐项实例化子树；规则逐项适用，而非各自创建业务 Store。不得用 /contacts/*/name 代替当前实例，通配符不是标准 JSON Pointer。

07

D5 · Identity：稳定实例身份

不让数组下标变化导致字段状态串位本轮采用
方案成本与问题取舍
数组下标作为 ID实现简单；删除、移动后旧字段状态可能错位不采用
强制业务数据包含 __id便于持久身份，但污染业务数据契约不采用
Runtime 独立 ID + 可选业务 Key适合无 ID 新建项，兼容业务回填与稳定映射采用
删除数组首项后的身份保留
操作前[0] Alice → r-a7
[1] Bob → r-b3
[2] Cindy → r-c9
操作后[0] Bob → r-b3
[1] Cindy → r-c9
索引变化，原实例不变
身份稳定是运行时承诺，数组下标只是数据当前位置。

允许：通过显式声明的业务 Key 辅助匹配已有项。不保证：没有业务 Key 时，任意服务端全量替换或跨会话数据恢复后都能精准认出原对象。

推迟到后续的细节 待细化

  • Append、Remove、Move、Replace 与批量回填时的 ID 保留规则；
  • 删除数组项后核心 meta/validation 的清理，以及通知 Host 处理相关外部请求的边界；核心不清理外部 Resource Store；
  • 稳定身份如何参与错误映射、Overlay 编辑上下文与 Scope 实例。
08

D6 · Binding：默认简单，复合受控

连接不同 ViewNode 与统一 Data，同时不提供任意双向脚本本轮采用

采用：默认单字段数据关联，复合物料使用具名 Binding Port；同一关联可供编辑或展示，能力由 Material Adapter 声明，修改统一走 Command，不在 Definition 再配 read/write 映射。

VIEW · 绑定形式示例 · 设计示意，非冻结语法
// 常规单字段输入
{ "material": "text-input", "bind": "/user/name" }

// 只读摘要；与编辑器读的是同一份 Data
{ "material": "text", "bind": "/user/name" }

// 受控复合组件：两个独立的数据槽位
{
  "material": "date-range",
  "bindings": {
    "start": "/period/startDate",
    "end": "/period/endDate"
  }
}
COMMAND · 候选命令，非冻结 · 设计示意，非冻结语法
// 复合物料通过一个受控对象 Patch 提交；字段名尚未冻结
{
  "op": "patch",
  "target": "/period",
  "value": {
    "startDate": "2026-10-01",
    "endDate": "2026-10-15"
  }
}

为何限制写回能力：fullName = firstName + " " + lastName 可以正向计算，却不存在可靠的通用逆向拆分算法。任意表达式双向绑定会让协议隐含一套写回程序。

一份 Data、多份 View：PC 平铺编辑，移动端摘要和详情弹窗，都通过同一 Reference/Scope 绑定相同工作数据。第四组已确认默认 Live Edit 同一 Work Data；只有真正隔离/撤销需求才由未来明确需求下额外声明，不能复制另一套 Binding 语言。

推迟到后续的细节 待细化

  • 单/多绑定槽位的值类型、Material Adapter 端口的编辑能力、错误传播；
  • 第三组已原则确认一次逻辑修改稳定发布、执行失败不部分成功；复合修改与同步 Reaction 的具体结算和校验顺序交 L3 细化；
  • 复合组件如何适配输入/输出格式，而不侵入数据结构。
09

D7 · Initialization：原则先定、生命周期后议

回填优先与 Missing 补缺原则已确定；完整生命周期仍后议原则确定

本轮采用的原则是：显式提供的已有数据优先于默认值；默认值只填补按约定判定为 Missing 的位置。 null、空字符串、0 不应自动被视为缺失。

场景阶段性语义仍待决定
新建表单从显式初始数据开始，按规定补齐缺失默认项默认值存储位置、深层合并粒度
编辑/回填已有数据优先，不被默认值静默覆盖不兼容类型、未知字段处理
草稿恢复草稿与权威源之间需要明确的恢复策略版本、冲突、变更归属
ResetF2 推荐恢复最近明确建立的初始化基准，不默认重放逐字段编辑推荐未升格为已确认；具体基准/API/范围及状态清理继续细化
D7 已确认的初始化原则

JSON Schema 的 default 仅是声明信息，不自动修改表单数据；实际合并与初始化属于 L3 的生命周期职责。这里不能把默认值策略、异步回填、草稿恢复混成一个隐式流程。

跨层职责：哪些问题明确不放进 L1？

关注点L1 定义其他层执行
Data Schema目标数据结构及可声明的元数据L2 结构检查；L3 管理 Working Data
