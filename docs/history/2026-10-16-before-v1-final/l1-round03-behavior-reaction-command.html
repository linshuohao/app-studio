03

继承第一、二组的约束

第三组不是独立的规则系统，而是组合前两组已经确定的基础语义。下面这些结论是行为模型的前置约束。

来源已形成的共识第三组的约束
架构基线L1 Definition → L2 Preparation → L3 Form Runtime → L4 Renderer行为定义在 L1；调度与执行在 L3；渲染与 UI 局部交互在 L4。
第一组 · DataData 与 View 独立；唯一权威 Form Working DataReaction 和 Command 只作用于业务数据，不在 View 创建第二套真值。
第一组 · Value工作数据可暂不满足 Schema；解析仅成功或失败；Missing ≠ null业务校验失败不等同于事务失败；Remove 不得与 Set(null) 混为一谈。
第一组 · Reference / Scope类型化引用 + JSON Pointer；词法 Scope；数组项 Runtime 稳定身份Reaction 监听/目标复用同一套引用与作用域，不另起路径语言。
第一组 · Binding一对一绑定默认，受控复合绑定按需扩展View / Host 通过统一数据修改入口发起变更。
第二组 · Expression受控动态槽位；纯 JSON AST；命名复用；Pure FunctionReaction.when 使用纯 AST，赋值使用递归 ValueSpec 内显式 $expr；Expression 不执行写入或 I/O。
第二组 · ConstraintJSON Schema 基础约束 + 独立复杂同步约束Constraint 负责合法性；Reaction 负责数据修改；二者不能混成一套规则。
延续既有边界，不恢复被否决的抽象

不恢复平级 Computation DSL；不允许 Expression 任意执行函数副作用；不为不同 View 各自维护权威数据；不为了远程选项而把 Resource Store 加进 Runtime。

第三组需要的新增协议核心仅为：Reaction 声明 + 受控 Command 意图。

05

最小行为模型：Command + Reaction

在 L1 中，我们把第三组核心收敛为两个可复用的领域概念：Command 描述“改什么”，Reaction 描述“何时在内部联动修改”。并不新增一个涵盖所有事件、查询、资源和异步动作的通用 Behavior 工作流。

行为声明的最小关系
View / Host 的操作意图用户编辑、受控组件修改、宿主明确更新
↓
Command设置、替换、局部修改、数组与批量修改
↓
Form Working Data唯一权威业务编辑状态
↓ 数据变化可匹配
Reactionwatch 多引用 + when Expression + then 同步 Command
↓
新的受控数据修改具体结算与稳定发布在 L3 设计
Expression 只计算；Constraint 只判定合法性；外部服务不成为上述内部链路的一环。
应该采用 Reaction

国家变化后清空城市；联系人的类型改变后删除不再适用的字段；用户选择某个模式后统一重置另一组输入。

不需要 Reaction

总价的纯派生；字段显隐；表单字段是否必填；远程下拉选项请求；打开弹窗和点击普通视图按钮。

06

B1 · Command 能力边界

B1 · Command原则确认

Command 不是通用 Action，也不是调用业务函数的接口。它只描述表单业务数据的受控修改意图，可以由 View / Host 主动发起，也可以由 Reaction 声明产生。

最小语义示例意图说明
Set / Replace替换 /address 对象父对象整体替换可令未包含的属性缺失。
Patch局部更新 /address/country与整个对象 Replace 不同，不应隐式删除其余字段。
Remove删除 /address/city 属性与显式写入 null 区分。
Array Insert在联系人列表中插入一项稳定实例身份由运行时维护。
Array Remove删除一项联系人处理实例生命周期，不等同于简单字段赋空。
Array Move调整联系人顺序同一个项移动后仍保留身份。
Batch / Composite一次操作更新多个字段表达一个逻辑上共同提交的修改意图。
TS · Command 的替换 / 局部修改区别
// 示意 API：一次写入整个对象
form.setValue('/address', {
  country: 'JP',
  province: 'Tokyo',
  city: 'Shinjuku'
});

// 与局部修改不同（API 名称未冻结）
form.patchValue('/address', { country: 'JP' });

一个 Command 可以在逻辑上影响多个值，不应强制拆为多个外部调用；Command 与 Change 不是 1:1 的关系。具体数据 Patch API 是否直接复用 JSON Patch，仍待协议统一阶段决定。

明确不支持

executeCode、任意副作用函数、直接网络请求、通用流程动作或允许自定义 Command 执行器绕过数据所有权；复杂纯计算走 Pure Function，外部动作走 Host。

07

B2 · Reaction 声明模型

B2 / B3 · Reaction原则确认

规则入口可用第六组统一 ScopeBinder 独立绑定对象/数组，数据身份仍归 L3。Reaction 的最低限度能力是 watch（触发引用） + when（可选判断） + then（同步数据修改），并复用第一组的 Reference / Scope 与第二组的 Expression。

JSON · 多触发源 Reaction · 字段名示意
{
  "id": "clear-city",
  "watch": [
    "/country",
    "/province"
  ],
  "when": {
    "use": "cityIsNotApplicable"
  },
  "then": [
    {
      "op": "set",
      "target": "/city",
      "value": null
    }
  ]
}

已明确的 L1 语义

多个 watch 引用任意一个被监听的数据引用发生实际变化，即可使该规则成为触发候选；默认按 OR 语义理解。
条件与触发分离when 是执行时读取当前数据的纯判断；其读取依赖不会自动追加为 watch。
同步且只修改表单数据then 不允许进行 HTTP、SDK 调用或异步副作用；其结果是受控 Command。
复用词法作用域重复数组项内的一条规则定义可实例化于不同作用域，不为每项重新写规则。

不扩展为通用事件表达式语言

第六组只保留 Material Event → form.command / host.emit 的受限连接；呈现归容器 Material。该连接不是 Reaction 触发源，不建立通用事件 DSL。不提供任意 AND / OR 事件时序组合、全局事件总线或者“服务调用成功就触发下一步 Action”的工作流规则。用户点击、组件展开属于 View Intent；初始化、Reset 等属于 Lifecycle。是否支持 Context Change 主动触发 Reaction，留待生命周期与统一协议阶段评估。

需要避免的语义歧义

“当国家是 JP 时执行”描述的是状态条件，而不是事件。更准确的声明是“国家发生变化时，如果当前条件满足，执行赋值”。因此 watch 与 when 不应混为一个字段。

08

Expression 如何进入 Behavior

B4 · Expression in Behavior原则确认

上一组已经决定：Expression 只允许位于协议声明的动态槽位，并采用统一的纯 AST。第三组直接复用这一规则，不再新增联动专用表达式语法。

位置语义设计边界
Reaction when纯布尔条件表达式只能读取当前状态，不可写回数据。
Command value静态字面量或表达式求值结果属于递归 ValueSpec；内部显式 $expr 由 L2 发现，不扫描任意 JSON。
Reaction watch受控 Data Reference 列表不得通过任意表达式拼接动态路径。
Command target明确的 Reference / Scope只能定位合法可写数据目标。
View 的显隐／禁用仍通过 View Dynamic Slot + Expression纯派生不应转写成 Reaction 修改 View 状态。
JSON · 动态写入示例；仅当业务确实需要持久化派生结果
{
  "watch": [
    "/quantity"
  ],
  "when": {
    "op": "gt",
    "args": [
      {
        "ref": "/quantity"
      },
      0
    ]
  },
  "then": [
    {
      "op": "set",
      "target": "/lastCalculatedAmount",
      "value": {
        "$expr": {
          "op": "mul",
          "args": [
            {
              "ref": "/price"
            },
            {
              "ref": "/quantity"
            }
          ]
        }
      }
    }
  ]
}

通常 price × quantity 应直接用 Expression 派生，并不需要写入 Form Data。上面的示例仅说明 Command 值可以使用表达式，不能被理解为默认推荐把派生值持久化。

09

修改对象与变化引用的关系

B5 · Command ≠ Change已确认

一次替换对象只需一个 Command，却可能改变多个数据引用。这种行为应当存在，不必为每个子属性制造独立 Command，也不必把对象修改视作多个并发写入。

原数据
JSON · 当前 Work Data
{
  "address": {
    "country": "CN",
    "province": "Guangdong",
    "city": "Shenzhen"
  }
}
写入的新对象
JSON · Replace /address
{
  "address": {
    "country": "JP",
    "province": "Tokyo",
    "city": "Shinjuku"
  }
}
一次操作可以影响多条声明式依赖
Command: Replace /address一个逻辑修改操作
↓
/address/country旧 CN → 新 JP
/address/city旧 Shenzhen → 新 Shinjuku
↓
匹配对应 watch 的 Reaction至于差异提取、索引与去重算法，属于 L2/L3

需要在 L1 说明“数据实际变化”的可观察含义，但不在本轮规定具体 Diff 算法。对于对象等值性、嵌套数组移动与旧/新 Scope 映射，列入后续 Runtime 验证。

10

同步联动与覆盖原则

B7 · Overwrite Semantics原则确认

此前考虑过：只要多个 Reaction 写同一个字段便视为冲突、引入优先级或拒绝事务。经过讨论，我们认为这对同步表单联动而言有明显的过度抽象倾向。

方案结果阶段性判断
同目标写入默认报错不允许不同规则依次覆盖同一字段未采用：会误伤合理的同步联动。
规则声明 priority由复杂优先级决定最终值未采用：为配置增加新概念。
确定顺序、后写覆盖同步规则按约定顺序执行，后一次赋值成为当前值当前倾向：简单、可解释、可调试。
JS · 覆盖关系示意；具体跨轮调度细节未冻结
// 定义中按顺序声明，演示两条针对同一 watch 的规则
reactions: [
  { watch: ['/country'], then: [{ op: 'set', target: '/province', value: null }] },
  { watch: ['/country'], then: [{ op: 'set', target: '/province', value: 'Tokyo' }] }
]
// 候选语义：先写 null，再写 Tokyo，最终为 Tokyo

JS 单线程并不意味着可以忽视行为确定性。两个同步规则不是多线程数据竞争，但如果顺序不明确，最终业务值仍会因配置排列或调度策略而变化。因此需要明确稳定顺序与诊断，但没有必要新增通用写入冲突 DSL。

尚未冻结的执行细节

“按 Definition 声明顺序”和“联动进一步级联后的跨轮顺序”目前是设计倾向，具体如何结算、去重、设置循环上限，以及在同一 Batch 显式赋值与 Reaction 覆盖时如何做一致性验证，归 L3 执行规则专题。

11

事务的可观察语义

B6 · Transaction Boundary原则确认

我们保留稳定发布、失败不部分提交的语义要求，但不把事务算法放进 L1。事务存在的原因不是 JavaScript 同步并发，而是避免观察者看见多步联动中不一致的业务状态。

L1 对外要求，而非 L3 实现图
Command 提出数据修改意图可替换对象，亦可一次批量修改
↓
Runtime 处理相关同步 Reaction执行期间候选数据由内部结算
↓
稳定结果对外可见View / Host 观察已完成的逻辑修改
情况对外期待为什么
输入不满足业务约束允许写入工作数据并呈现 Validation Issue数据的业务无效不等于事务执行失败。
工作值暂无法按目标类型解析按 D2 接纳工作态并标识解析失败不为了表单完整合法而阻断普通编辑。
Command 的目标或执行语义非法不发布半成品修改；返回可诊断错误属于执行失败而非业务校验失败。
同步 Reaction 不终止不可无限执行；不能宣布部分成功需要 L2/L3 的循环与预算保护。

Draft / Patch Log、依赖索引、稳定快照生产、回滚方式、相等性比较与同步调度器都属于 L3。L1 只声明它必须产生什么样的可观察结果。

外部资源与跨端适配

EXT-1 / EXT-2 · External Boundary不纳入核心

动态表单需要外部数据，不代表表单引擎应当执行外部请求。远程搜索、网络缓存、HTTP/SDK 调用、上传、订单提交与工作流均应由 Host / View Adapter 承担。

场景：国家变化后远程加载省份选项

推荐的数据与责任流向
Form Engine 的 /country 发生变化内部受控数据修改及 Reaction 结算
↓ 外部订阅 / View 读取
Host / View DataSource Adapter使用 Fetch、Dio、Native SDK 或共享 Query Store
↓ 远程请求及结果状态归外部
外部 Province OptionsLoading / Error / Cache 属于外部
↓ 用户选择一个省份
Command: Set /province将真正的业务选择写回表单
信息或行为所有者原因
/province 选中值Form Working Data属于用户正在编辑的业务数据。
provinceOptions 候选列表Host / View Adapter属于远程读取的外部数据。
Loading / Error / Retry / CacheHost / View Adapter不应侵入核心的事务和依赖体系。
地址自动填充结果Host 接收后通过 Command 写入外部结果不能直接绕过数据所有权。
calendar.ageAtDate 等纯函数受控 Pure Function 扩展是纯计算，不执行网络副作用。

跨端一致性的合理范围

同一表单的 Data、同步表达式、Constraint 和 Reaction 具有统一的业务语义；网络客户端、认证、请求协议、缓存和远程选项组件实现可以因 Web / Flutter 而不同。不需要提供一个全局 Universal Capability Registry 来消除所有平台差异。

重要的边界折中

外部资源查询即使由动态数据触发，也不会自动成为 Reaction；远程结果即使被用于显示，也不会自动成为 Form Data。需要写入表单时，使用显式的受控 Command。

14

外部校验：义务 + 被动五态 + 有效性 + Readiness

本节按后确认的第五组 F4/F5 修订；第三组最初仅考虑可选 Issue 注入的方向已被扩展。Host 执行外部校验，Runtime 必须知道已声明/注册的义务及当前验证事实，但不驱动网络请求。

Definition 声明固有外部校验 ID、依赖、目标、适用条件和是否必需；Host 可补充环境义务，正式 Readiness 判断前应完成必需注册，同 ID/Scope 不能静默覆盖。Runtime 被动登记 Unverified / Pending / Valid / Invalid / Error、Issues 及结论有效性，Host 管理请求、防抖、超时、重试和提交。

五态不是五种 ParseResult：值解析仍只有成功/失败。适用性为独立维度，不能将无法判定的必需项当作通过；issues=[] 不证明已验证。对每项必需校验，只有适用于当前依赖的 Valid 结论才满足 Readiness。

结论要区分实例、规则、Scope、依赖状态及一次调用；依赖变化或 Host 主动失效后，不接受旧结果，包括 alice→bob→alice 的 ABA 情形；无关字段变化不应自动失效。具体 token、索引与 API 均未冻结。

Runtime Ready 仅证明当前已声明/注册、适用且必需的内部和外部校验满足：当前工作值可生成符合契约的输出，同步约束通过，必需外部项全为当前有效 Valid，且报告/输出/义务目录对应一致状态。未知适用性、Unverified、Pending、Invalid 或 Error 的必需项都不能放行。

Host 仍决定权限、业务条件与真实提交，并在异步等待后复核当前报告和输出。Ready 不等于服务端批准、HTTP 成功或业务提交许可；Runtime 不发网络请求，也不以校验状态自动挂起/恢复 Reaction。

外部状态更新不自动触发、暂停或恢复同步 Reaction；Host 需要异步后续修改时发出新 Command。具体 request token、报告结构、API 与生命周期实现未冻结。详见 被动上报语义示例。

已否决与移出核心的方案

为防止后续设计反复漂移，本节记录哪些方案经过讨论后被明确收缩、推迟或移出了核心。

曾讨论的方案现阶段处理原因
通用 Event Bus不采用不同应用事件、View 局部交互和数据触发不应混成同一语言。
异步 Reaction / Action Pipeline不采用把业务请求、重试和工作流带进表单内核。
内置 Query Resource Engine不纳入核心远程数据的获取和缓存应由 Host / View Adapter 持有。
Universal Capability Registry不采用为核心基础设施内部Pure Function 扩展已经足够；外部 I/O 不需被引擎统一执行。
通用 Result Router不采用结果归属应由明确边界定义，不提供任意目标分发 DSL。
同目标写入默认强制报错不作为默认约束JS 同步执行具有顺序，业务覆盖不是线程竞争；可做静态告警。
为 Reaction 定义 priority / 冲突仲裁V1 暂不做增加配置心智负担，收益尚未证明。
在 L1 冻结 Diff / 调度 / 回滚算法推迟到 L3超出 Definition 的职责范围。
收缩不等于删除能力

外部查询、服务端校验、上传、复杂工作流依然可以存在于完整产品中，只是由 Host 或相应业务系统负责。Form Engine 不因为“能表达”就承担“必须执行”。

L1—L4 的职责交接

第三组讨论一度深入到了“分几轮联动、Diff 怎么做、事务异常怎么回滚”，本节专门记录本次纠偏后的分层边界。

层 / 角色需要负责本轮不做
L1 DefinitionCommand 操作语义、Reaction 的 watch / when / then、Reference/Expression；F4 固有外部义务及依赖/适用条件，结果的可观察要求。不定义线程模型、队列、索引与缓存实现。
L2 Preparation结构规范化、引用解析、纯函数与类型检查、可分析的规则触发/依赖关系、潜在循环诊断。不负责真正执行事务或网络请求。
L3 Form Runtime受控状态修改、候选状态结算、联动去重、级联、变更识别、实例身份、稳定发布；并按 F4/F5 登记被动校验义务/五态/有效性、统一 Report / Readiness / Output。不承担 HTTP、上传、外部业务流程。
L4 Renderer读取数据与校验状态、发出修改意图、维护局部 UI 状态、多端 View 实现。不拥有第二份权威表单业务数据。
Host / App远程查询、异步校验执行、应用级副作用、提交与持久化，适配不同端。不直接绕过 Command 修改 Form Working Data。

属于 L1 的要求

“Reaction 可监听多个引用”“Command 只修改表单数据”“一个逻辑修改完成后对外可见稳定结果”“表达式不可执行外部副作用”。

“Reaction 先入先出还是按轮次调度”“对象递归 Diff 或依赖索引”“如何存储 Patch Log”“是否用 Proxy / Immutable Draft”。

最终决策摘要与冻结范围

第三组最终决策结论

Form Engine 是面向结构化表单数据的确定性状态事务引擎。L1 第三组只新增受控 Command 与同步 Reaction 两项核心行为语义：Command 描述表单数据修改；Reaction 通过多 Reference 触发与纯条件声明内部联动。 Expression、Constraint、Reference、Scope 均复用前两组；外部查询、异步业务操作及工作流由 Host 承担，不建设通用 Resource / Capability / Event / Result Routing 体系。

可视为已收敛的 8 条原则

01

核心职责明确

引擎处理表单内部数据状态、事务、同步联动、纯计算与约束。

02

唯一修改入口

View、Host 和 Reaction 对业务数据的变更统一通过受控 Command。

03

最小化 Reaction

多 watch + 可选 when + 同步 then，不建立事件编排系统。

04

纯派生不写回

Expression 解决派生计算；只有确实需要改变 Data 时才使用 Command。

05

一个操作可以影响多个数据引用

对象替换、数组修改是自然的 Command 语义；变化识别属于 Runtime。

06

稳定状态对外发布

同步联动应收敛为一致结果；不将校验无效误判为事务执行错误。

07

不引入通用写入冲突 DSL

按确定顺序覆盖、可诊断；优先级、并发写锁与冲突仲裁不作为 L1 V1 必备抽象。

08

外部副作用留在 Host

资源获取、远程校验执行、上传、提交、工作流不得隐式进入核心。
