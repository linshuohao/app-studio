01

文档定位与定稿范围

ADR 05 · 设计边界

把“外部校验是否完成、是否仍有效”纳入表单实例契约，但不把“如何执行外部校验”带进引擎。

这一份归档记录第五组 Form Lifecycle / Editing Context / Validation / Submission 的讨论结果、架构取舍、代价与被排除的设计。它属于 L1 领域模型和表单实例契约的阶段性 ADR，不是已经冻结的 JSON Schema、TypeScript SDK 或 L3 实现方案。

本组真正的问题不是“如何执行生命周期状态机”，而是：Definition 声明哪些义务，Runtime 应当保证哪些一致性，Host 管理哪些外部副作用。

核心结论：表单只有一份权威 Work Data；引擎知道校验要求、当前结论和输出是否具备校验条件，但不发起外部网络请求，不执行提交流程，也不等待异步 Reaction。

状态解释如下：已确认指本次或前序讨论明确认可；原则确认指架构方向确定但接口未冻结；推荐保留指没有逐项获得最终确认但符合现有共识；待细化指留给第六组协议收敛或 L2/L3。

类型 本组交付 不在本组展开
L1 Definition 默认值语义、固有外部校验声明、约束依赖与适用条件 API 地址、请求重试和网络执行器
Form Instance Contract Update / Reinitialize / Reset 的区别、校验状态一致性、Readiness、输出契约 内部调度算法、持久化与快照策略
Host Contract 提供初始值、补充外部校验、上报状态、发起提交 外部业务工作流的通用 DSL
Renderer / View 显示 Issues 和 Pending；直接编辑唯一 Work Data 由 Modal 创建第二个权威数据源

05

F1：初始化默认值与外部输入

候选方案：A 完全由 Host 补齐数据；B Definition 负责一切初始化；C Definition 声明静态默认值、Host 供应已有数据、引擎按“缺失补全”合成。当前推荐 C。

方案 价值 代价 / 风险 结论
A：全部交 Host 引擎最简 多端宿主重复补缺；跨端初始状态不易一致 不优先
B：Definition 负责初始化流程 逻辑集中 易侵入异步取数、条件编排、流程系统 不采纳
C：静态默认值 + Host 初始值 规则一致、责任明确、配置成本低 需精确定义对象/数组及缺失语义 推荐

示例：

JSON · 语义示例 / 非冻结协议
{
  "defaults": {
    "country": "CN",
    "city": ""
  },
  "initialValuesFromHost": {
    "country": "JP",
    "city": null
  }
}

合成结果：country = "JP"，city = null；不能因为 null 看起来像“空”就把它覆盖为默认空字符串。上面的键只用于解释，initialValuesFromHost 不属于必须写入 L1 的字段。

补缺规则的对象递归深度、数组项默认值、类型不匹配时的报错，以及 JSON Schema default 如何应用，统一留给协议细化。特别注意：JSON Schema 的 default 是注解，不代表通用校验器会自动写入数据。

06

F2：Update、Reinitialize、Reset 的语义区分

同一个数据值变化，在不同场景下可能拥有不同含义：用户手动切换国家需要触发清空城市；Host 装载一条完整新记录则不应把已回填的城市清掉。

操作 意图 与普通 Reaction 的关系 基准状态
Update 修改当前实例中的部分数据 正常参与同步联动 通常不更新基准
Reinitialize / Replace 用新的已有数据建立或重建实例内容 不默认模拟逐字段编辑 重建初始化基准
Reset 恢复本次初始化基准 不默认模拟逐字段编辑 保留原基准
TEXT · 语义示例 / 非冻结协议
Definition 默认：country = CN
Host 初始值： country = JP
初始化基准：    country = JP
用户修改：      country = US
Reset 后：      country = JP

“基准快照”是用于恢复或派生 Dirty 的不可编辑参考，不是另一份参加联动的权威 Work Data；因此不会违反第一组的单一数据源原则。

推荐选择：区分三类实例操作；Reset 恢复“该实例最近一次明确建立的初始化基准”，而不是固有默认值。回填部分字段到底是 Update 还是重建基准，必须由 Host 显式选择，不应根据传了几个属性去猜测。

07

F3：Live Editing 及真正的暂存编辑边界

PC 平铺输入、移动端摘要卡片进入详情 Modal、平板 Drawer，默认只是不同 View：它们通过 Binding 编辑同一份 Work Data，改动立即触发同步 Reaction 和数据驱动的 Constraint。

场景 默认语义 是否需要新数据源
Modal 打开 / 关闭 UI State，由 Material 或 View Controller 管理 不需要
在 Modal 修改字段 立即修改 Form Runtime 的当前 Work Data 不需要
“完成”关闭详情 仅表示结束展示 / 编辑入口 不需要
“取消”明确要求放弃所有修改 需要独立的撤销或暂存语义 不能假装关闭就回滚

如果业务未来确实需要“确认前完全隔离、取消时完全丢弃”，可以评审独立表单实例或明确的 Editing Session。但不让这一少数需求反向决定所有 Modal 的默认实现。

此决策与第四组 V7 一致：View State 不是业务数据的另一份副本。

08

F4 的关键转折：为什么只有 Issues 不够

起初考虑让 Host 仅调用 setExternalIssues({ source, issues })，使视图能够集中展示服务端错误。后来发现：issues: [] 有多种互相矛盾的含义。

issues: [] 可能代表 可以允许提交吗？
此次校验已通过且对应当前值 可以，若其他约束也通过
尚未发起校验 不可以（对必需校验）
请求仍在进行 不可以
旧结论已经过期 不可以
请求失败，无法判断是否合法 不可以

因此外部校验至少要具备：事先可识别的校验义务、执行结果状态、Issues 和有效性约束。这不是为了 UI 展示新增状态，而是为了让引擎对“当前已知的验证要求是否全部完成”给出可靠回答。

讨论修订：从 Issue Injection 扩展为 External Validation Contract + Passive Status + Issues + Readiness。原方案不是错在不能显示错误，而是无法证明“无错误＝已经完成验证”。

09

F4-A：类型失败、同步约束失败、外部业务失败

必须避免把所有 Invalid 合并为一个全局开关。

层级 举例 影响范围 不能做什么
Value 解析失败 数字输入 abc 依赖数值的 Expression 无法正常求值 不把求值失败当作 false 或沿用旧值
同步 Constraint 未通过 年龄小于 18 不满足购买条件 生成业务 Issue，相关条件表达式可以明确判断 不暂停整个表单的所有 Reaction
外部校验 Invalid 用户名已存在 相应校验未通过、影响 Readiness 不自动撤销其它联动
外部校验 Error 请求超时或服务故障 当前没有可用结论 不把技术错误当用户输入错误

举例：国家改变后，需要清理已经不适用的城市。即便新国家不是允许投保的国家，这条清理数据的 Reaction 仍可能必须执行。所以不要把“任何业务校验失败”设计为 Reaction 的全局熔断器。

确定的边界：Reaction 以 Data Change 为触发来源；when 无法得到合法布尔结果时不能执行对应 Command，但应保留可诊断性。Constraint 失败不会自动中断其他无关联动。同步约束可以与 when 共享同一个命名 Expression，以复用业务条件。

10

F4-B：校验义务由 Definition 与 Host 共同提供

已经选择的架构方向是：Definition 声明表单固有外部校验；Host 可补充宿主或环境相关校验。

校验义务至少说明：唯一 ID、所依赖的数据引用、校验问题的归属位置、何时适用、是否属于提交前必需。它不声明 URL、fetch 方法、凭据、重试、超时或副作用工作流。

JSON · 语义示例 / 非冻结协议
{
  "constraints": [
    {
      "id": "username-unique",
      "kind": "external",
      "dependsOn": [
        "/username"
      ],
      "target": "/username",
      "requiredForSubmit": true
    },
    {
      "id": "age-eligible",
      "kind": "internal",
      "assert": {
        "op": "gte",
        "args": [
          {
            "ref": "/age"
          },
          18
        ]
      },
      "target": "/age",
      "errorCode": "AGE_TOO_SMALL"
    }
  ]
}

上述为候选协议形状，不是 JSON 最终定稿。是否使用 kind、是否统一放入 constraints、when 和 requiredForSubmit 的精确位置，精确 Schema 仍需收敛。

Host 补充的约束与 Definition 约束进入统一的规则目录，不能在同 ID、同 Scope 下静默覆盖。Host 必须在 Runtime 对提交 Readiness 作正式判断前完成必需义务注册，否则“全部完成”仅意味着已注册的规则完成，不意味着宿主所有业务检查完成。

11

为什么引擎必须提前知道必需校验

如果 Runtime 只见到 reportValidation({id, status:'valid'})，那么在 Host 尚未调用任何上报接口之前，Runtime 不知道这个校验是否存在，更无从得知还有哪项检查未完成。

TEXT · 语义示例 / 非冻结协议
Definition / Host 注册校验义务
             ↓
    Runtime 建立已知义务集合
             ↓
  当前数据对应初始 Unverified
             ↓
    Host 选择何时发起请求
             ↓
 Host 报告 Pending / 结果
             ↓
 Runtime 汇总已知校验是否齐备

重点是：声明校验存在 ≠ 引擎主动执行校验。 外部请求仍然需要 Host 自己安排，可以立即执行、节流、失焦后执行或在提交时执行。

12

F4-C：最小外部校验状态集合

Unverified没有当前有效结论
Pending外部检查正在进行
Valid当前数据已通过
Invalid业务约束未通过
Error技术失败，无法判断
状态 精确定义 必需校验是否满足
unverified 当前适用依赖尚无可用结果；也用于旧结果失效后 否
pending Host 已登记正在校验当前目标数据 否
valid 已获得适用于当前依赖的通过结论 是
invalid 已获得适用于当前依赖的业务不通过结论，可附 Issues 否
error 校验调用出现技术性失败，尚无合法性结论 否

这里不另设 incomplete 类型解析状态；第一组已经明确 Value 的 Parse 只有成功或失败。上表是外部校验结论状态，与 Value 的类型合法性是不同维度。

另外，适用性（applicable / not applicable / cannot determine）不是第六个“任务状态”。对不适用的可选规则，可以不纳入当前 Readiness；但如果规则适用条件无法求值，不应把它默认为通过，必需规则需要保守地阻断准备完成并提供诊断。

13

校验结论如何和当前数据保持一致

这项契约应在 L1 阶段明确正确性要求，但无需讨论 L3 的令牌、索引和调度算法。

TEXT · 语义示例 / 非冻结协议
T1：username = alice → Host 检查 Alice → Pending
T2：用户输入 bob   → Alice 的结果必须失效
T3：Host 检查 Bob   → Pending
T4：Alice 返回 Invalid → 不得污染 Bob 的状态
T5：Bob 返回 Valid   → 当前校验变为 Valid

一项结论至少需要能够在语义上区分：Form Instance、Constraint ID、Scope Instance、依赖数据状态及具体一次调用。

维度 为什么需要
Form Instance 防止另一份表单的结果误入当前实例
Constraint ID 区分不同业务义务，解决同字段多规则
Scope Identity 删除、插入、移动数组后仍能定位正确项
Dependency State 数据依赖改变后让旧结论失效；无关字段改变不必失效
Invocation Identity 旧请求晚到不能覆盖新请求结果，避免 ABA 误判

ABA 边界：alice → bob → alice 不能仅凭值重新相同就随意接受之前已经被判定过期的调用结果。缓存复用或结果恢复需要明确的策略，不能作为协议默认假设。

另一个边界是外部事实可能变化：即使 Form Data 一直是 alice，用户名也可能后来被别人在服务端注册。因此 Host 必须能够显式失效已登记结论，时效和再次检查策略仍由 Host 控制。

Host 被动上报接口：语义示例

token 在此只是占位符，表示“同一次依赖状态下的特定校验尝试”；并不意味着一定以全局版本号、随机 UUID 或字符串 token 实现。重要的是过期结果不再被接受作为当前有效结论。

上报 pending 不会自动发起请求；上报 valid 也不会自动触发同步 Reaction。两项决策必须同时成立。

F4-D：外部校验与同步 Reaction 明确解耦

这项已按用户选择确认：外部校验不自动阻断、恢复或重新触发同步 Reaction；异步结果导致的数据操作，由 Host 发出新的普通 Command。

发生的事 行为归属
用户改字段 Binding / Host → Runtime Command
Data Change 触发纯业务联动 Runtime 同步 Reaction
Expression 不能合法求值 相关计算不产出伪造结果，记录诊断
同步 Constraint 失败 产生 Issue，不全局屏蔽其它 Reaction
外部校验 Pending / Invalid 更新被动校验状态，不暂停同步联动
外部校验 Valid 后需要自动填城市 Host 检查仍匹配当前输入，随后发送 Command

被否决的方案：Reaction 自动等待外部校验、在未来异步完成时自动恢复执行。这会引入悬挂任务、版本核对、队列生命周期、取消与级联复杂度，重新演化为异步规则引擎。

内部错误与外部 Issues 的归属

外部校验 invalid 可以携带标准化 Issues，与内部校验共同供 View 消费，但错误不绑定某一个 ViewNode ID。

最小定位语义包括：来源（内部 / 外部）、Rule ID、Data Reference、Scope Identity、错误 Code，以及可选展示参数。

读取方 实际所需信息
PC Field 当前字段的错误及提示
Mobile Summary Card 当前对象或数组项相关错误聚合
表单错误汇总 全部适用 Issues
Host Submit 阻断原因、进行中或未执行的规则
Runtime Validation 当前值和所登记结果是否仍匹配

View 的 touched、提交尝试或“失焦后显示”是呈现策略；它不决定校验是否真实通过。invalid 应与技术性 error 区分，避免把“网络错误”误展示为“用户输入不合法”。

17

F5：Validation Readiness 的确定性条件

Submission Readiness
Data 可解析且内部约束通过类型合法 · 同步验证完成
＋
已登记、适用、必需的外部约束全部 Valid没有 Pending / Unverified / Invalid / Error / 无法判定的必需项
↓
Runtime Readiness仅表示已知校验条件满足，不代表 Host 业务放行

Readiness 只回答：“当前已声明和已注册、适用于当前表单数据、必须通过的校验要求是否全部满足？” 它不是业务最终审批，也不是服务端提交成功。

准备就绪须同时满足：

  1. 当前工作数据能按 Data Schema 正确解析/规范化生成输出。
  2. 当前必需的内部 JSON Schema 与同步 Constraint 校验通过。
  3. 所有当前适用且标记为提交必需的外部校验都拥有当前数据有效的 valid 结论。
  4. 必需外部约束没有 pending、unverified、invalid、error，也没有无法判定适用性的规则。
  5. 判断与输出对应同一一致的数据状态，注册的校验义务集合也是当前有效版本。
内部校验 / 输出 必需外部校验 Runtime Readiness
通过 全部当前 valid Ready
通过 存在 pending Not Ready · 等待
通过 存在 unverified Not Ready · 未验证
通过 存在 invalid Not Ready · 业务不合法
通过 存在 error Not Ready · 技术性失败
不通过 任意状态 Not Ready · 内部失败
通过 必需规则适用性无法求值 Not Ready · 无法确认

“没有 Issues”不是 Ready 的充分条件。适用且必需的校验状态必须明确为 Valid。

Readiness 与 Host 提交许可不是同一回事

TEXT · 语义示例 / 非冻结协议
Form Runtime                   Host Application
────────────                   ────────────────
校验内部约束                   接收提交意图
检查当前必需外部义务     →     等待 / 发起外部校验
生成 Readiness           →     核对权限 / 签名 / 服务端条件
输出规范化数据           →     HTTP 请求及响应处理

Runtime Ready 只证明引擎已知的校验要求被满足。Host 仍可能因为权限、服务端二次确认、会话失效、业务审批、库存等原因不允许提交。

提交前 Host 应重新核对当前数据与校验报告的一致性；如果用户在异步等待期间修改了相关数据，之前的许可不再有效。至于使用快照、修订号、只读提交句柄或其他实现方式，属于后续 L3 设计。

统一 Validation Report 的候选形状

TS · 语义示例 / 非冻结协议
// 说明语义，不冻结最终 SDK API
interface ValidationReport {
  dataRevision: string;
  internal: {
    valid: boolean;
    issues: ValidationIssue[];
  };
  external: {

最终 API 可以选择更明确的 blockedReasons、applicabilityUnknown、registryRevision 等字段。这里的计数仅用来说明报告需要同时表达问题、进行中情况与完整性；不能仅凭上述示例代码就认为已覆盖全部动态 Scope 与条件约束细节。

同一份报告可被 Field、摘要卡片、错误汇总和 Host 使用，但它不应反过来承担 View 的错误显示时机或 Host 的请求调度职责。

F6：生命周期是实例契约，而不是流程引擎

实例能力 是否属于核心 备注
Create / Initialize 是 建立当前 Work Data 和基准
Update / Command 是 按正常表单联动修改
Reinitialize / Reset 是（语义推荐） 不模拟逐字段用户编辑
Validate / Read Report 是 同步结果 + 外部被动结果
Get Output 是 结构化规范化结果，失败则返回错误
Dispose 是 释放实例资源，不定义复杂业务流程
Dirty 可派生 与基准数据关系需要进一步定义
Touched 可选交互元数据 不等于业务校验状态
Loading / Submitting 默认 Host 不能混入单一互斥 Form Runtime 状态机
Submitted / Approved Host 是业务结果，不是表单内部生命周期

尤其不建议建立 Created → Initializing → Editing → Validating → Submitting → Approved 这样的统一状态机：这里混杂了可同时存在的 UI、校验与业务请求状态，含义并不互斥。

21

与 View Profile 的生命周期关系

切换 PC Expanded 与 Mobile Compact Profile 时，如果复用同一个 Form Instance，不应重新初始化 Work Data，不应通过逐字段 Update 重放初始值，也不应单纯因 View 切换而触发普通 Reaction。

若 Host 明确销毁旧实例并创建新实例，那是另一种完整生命周期操作，不能与“更换 View”混为一谈。

按需交付仅选择所需视图；不能因为当前 Profile 不显示某些字段，就自动删除其 Schema、Constraint、Reaction 或必需外部校验义务。Profile 裁剪不是业务规则裁剪，更不是数据权限控制。

这里的“成本”是相对工程成本，不是对某个项目报价。基于当前 V1 范围，从初期实现、跨端一致性、持续维护、边界风险四个维度比较。

关键场景验收清单

  • S1 · 默认值与 null：Host 显式 null 不被默认值覆盖，缺失项按规则补全。
  • S2 · Reset：从 JP 初始化、编辑到 US 后，Reset 回到 JP 而不是 Definition 默认 CN。
  • S3 · 回填：完整 Reinitialize 不因为 country 变化而清空已经回填的 city。
  • S4 · Modal：移动端详情编辑立即影响 Work Data，PC/摘要和同步联动可看到一致数据。
  • S5 · 类型失败：不能解析的 quantity 不参与需要数值的派生表达式，不被当成合法 0 或旧值。
  • S6 · 业务失败：年龄不达标可以产生 Issue，但必要的地址清理 Reaction 仍能执行。
  • S7 · 待校验：issues=[] 但 Username 校验 unverified，Readiness 必须是 Not Ready。
  • S8 · 请求乱序：Alice 请求晚返回不能改变当前 Bob 的外部校验状态。
  • S9 · 无关字段：修改手机号不自动撤销与用户名唯一性无关的校验结论。
  • S10 · 数组稳定身份：删除/移动联系人后旧结果不能错误关联到新位置的联系人。
  • S11 · 外部失败：网络超时展示技术性 Error，不伪造为业务 Invalid。
  • S12 · 提交并发修改：等待外部校验期间数据改变，旧 Readiness 不能给新数据放行。
  • S13 · Host 补充规则：新的必需检查注册后，Readiness 重新评估，不能仍使用旧完整性结论。
  • S14 · Profile 切换：只更换视图，不自动重置、重跑初始化或丢弃隐藏字段的校验义务。

这些是后续接口实现必须通过的语义验收场景，不是已经实现的自动化测试。

最终决策摘要与下一步

本组的最终边界：统一校验事实与提交准备程度，不统一网络执行、异步 Reaction 和业务提交流程。

本组收敛后，第五组最重要的架构变化不是增加生命周期 DSL，而是使表单的校验完整性变成可以可靠判断的实例契约。

  1. 初始化优先用简单的静态默认值与 Host 数据合成；Reset 与 Update / Reinitialize 语义区分，相关细节待最终确认。
  2. 默认所有 View（包括 Modal）实时编辑同一份 Work Data，不引入默认 Draft。
  3. 类型解析失败、同步业务约束失败、外部校验失败是不同维度；不能用一个全局 Invalid 阻止全部联动。
  4. Definition 声明固有外部校验，Host 允许补充；引擎只被动登记执行状态、Issues 和依赖有效性。
  5. 外部校验不自动阻断、恢复同步 Reaction；需异步验证后修改数据时由 Host 发送既有 Command。
  6. Runtime 提供当前已知校验的 Readiness 与一致的数据输出，Host 判断业务提交权限并执行请求。
  7. 不引入通用 Lifecycle / Resource / Async Reaction / Submission Workflow DSL。

阶段性定稿声明：F4 外部校验来源与 Reaction 边界已经由用户明确选择；F3、F5 和核心职责边界遵循前序确认；F1/F2 的默认策略保留为推荐，精确字段和实例 API 尚未冻结。第六组协议架构与原理组合验收已归档，当前优先补齐 Material Validation Metadata，再冻结 Canonical Schema 与实例/Host 精确接口。
