01

结论概览与归档口径

本文件归档L1 第四组 View / View Profile / Material / Interaction 的讨论与阶段性决策。它接续第一组 Data / Reference / Scope / Binding、第二组 Expression / Pure Function / Constraint、第三组 Behavior / Reaction / Command，并严格限制在 View Definition 的职责和可声明语义，不提前设计 L4 组件内部实现或 L3 调度机制。

一句话结论

一份 Form Data 对应多份独立 View Profile；视图以 Material 组合为主，复用统一 Binding 与 Expression；Material 负责内部交互，必要时通过受限 Event → Intent 映射连接其他视图、已有 Command 或宿主。移动端详情默认实时编辑同一份 Runtime Data。

状态标签如何解释

标记含义本文件中的处理方式

原则确认方向稳定，但必要语法和细节尚未正式冻结保留候选 JSON，不视为协议标准
待细化接口形状、边界场景或交付机制细节在 L1 收敛 / L2 / L4 / 第五组完善
不采纳过度抽象或与引擎边界冲突的方案记录否决理由，避免重复讨论

本文件所列 JSON、TypeScript 均是语义说明，不意味着字段名称、枚举和值域已发布 V1 正式协议。

03

继承前三组的不可破坏约束

既有结论第四组必须遵守的结果
Data 与 View 独立View 可以完全不同，但不能各自拥有权威业务数据
单一 Form Working DataModal、Card、PC Input 共享相同状态来源
类型化 Reference + Scope所有数据绑定和动态重复项沿用统一寻址规则
Binding 支持基础与复合关联普通输入简写、复合物料支持多个具名数据端口
Expression 纯计算、Dynamic Slot 受控物料属性需显式声明哪些位置允许表达式
Constraint 独立于 View错误按规则 / 数据引用 / Scope 归属，不绑定 UI 节点
Command 是数据修改唯一受控入口交互和物料不得绕过 Runtime 直接篡改 Work Data
Reaction 监听 Data 变化View 内不同点击行为不能复制或替代共享业务联动
外部请求由 Host 执行Material 可以调用宿主适配能力；Form Engine 不建立 Query Workflow

以上是本组设计的约束条件，不代表第四组需要重新设计这些公共基础抽象。

已确认同一 Data 的多端展示差异可以是视图结构差异，而不只是断点、CSS 或响应式布局的差异。因此多个 Profile 应允许完全独立的节点树。

Profile 名称不等同于设备名：PC 可以选择 Compact，平板也可以选择 Expanded。实际选择由 Host / Delivery 控制。

方案优势决定

基础树 + Profile Override可能减少配置重复不引入结构合并 / 补丁 DSL

07

V2 · ViewNode 最小化：Material 组合树

我们曾考虑为 Field、Display、Container、Card、Modal、Drawer、Tab、Step 都创建专用节点。经过讨论，认为这会将 Form View 演化为通用 UI 节点系统。

当前倾向：以 Material 组合树作为默认结构，只把真正与表单数据实例化相关的能力提升为协议语义。

统一 Material 组合的候选写法
{
  "material": "stack",
  "children": [
    { "material": "text-input", "bind": "/user/name" },
    { "material": "text", "bind": "/user/name" }
  ]
}
机制为什么需要归属
Material 节点决定使用哪个物料与其 Props / Slot 内容View Definition
Children / Slots组织 UI 容器和复合组件结构View Definition + Material Contract
Bind使物料关联数据字段第一组 Binding
Repeat / Scope从数据数组实例化多个子视图，保持动态项 Scope表单特有语义，需 L1 支持
Conditional Visibility根据 Expression 控制显示第二组 Dynamic Slot + Renderer
Modal / Drawer / Card具体视觉及呈现形式Material / Renderer，非核心专用 Node

特别注意：“Material + Binding + Children”尚不是正式的最终节点 Schema。它是最小设计方向；Slots 的数据类型、节点 ID 和 Repeat 的语法仍待细化。

08

V3 · Material Contract 与组件实现的边界

Material Manifest 的价值主要在于静态校验与跨端接入契约，并非描述每个组件内部的点击和布局实现。

Material Manifest · 候选形状
{
  "id": "contact-card",
  "props": {
    "title": { "type": "string", "dynamic": true }
  },
  "bindings": {
    "contact": { "type": "object" }
  },
  "events": {
    "edit": { "payload": "void" },
    "remove": { "payload": "void" }
  }
}

Manifest 可以描述 Props、具名 Binding Port、以及需要被外部消费的语义事件端口。组件内部保留完整的 UI 逻辑，无需把 Select 展开、光标更新、键盘组合输入等转换为 DSL。

Manifest 内容作用不承担
Props 类型与动态槽位识别合法配置、Expression 使用位置不实现计算或组件渲染
Binding Ports校验关联的数据端口与类型不定义第二套双向映射语言
Event Ports（可选）告知外界组件能发出哪些语义事件及 Payload 类型不定义内部点击逻辑
兼容性和版本定位 Web/Flutter 有无对应物料实现不要求相同平台组件实现

Web 与 Flutter 的组件可以在交互细节上不同，但引用同一 Material ID 时，必须满足对应的数据端口和必要语义事件契约。

09

V4 · Binding 只做数据关联

设计纠偏

协议不需要为每个字段反复配置 read / write 或自动生成双向映射。Binding 负责“这个节点关联哪一份数据”，能否编辑以及怎样提交变化由 Material Adapter 的能力决定。

编辑组件
编辑仍用普通 Binding
{
  "material": "text-input",
  "bind": "/user/name"
}
只读展示
无需另建 ReadOnlyBinding
{
  "material": "text",
  "bind": "/user/name"
}

如果同一 Input 的编辑能力受当前条件限制，使用已允许的动态物料属性，例如 readonly / disabled；但 UI 只读不等于业务权限控制。

复合控件仍可引用多个数据槽位：例如 DateRange 的 start 与 end。它的值更新方式来自 Material Adapter 契约，不需要在 Definition 中定义可逆的通用转换表达式。

复合 Binding · 候选示例
{
  "material": "date-range",
  "bindings": {
    "start": "/period/startDate",
    "end": "/period/endDate"
  }
}

数据发生修改时，不管 UI 来自 PC、移动 Modal 或外部 Host，最终都应进入第三组受控的 Command 接口。

V5 · 为什么不能完全删除 View Interaction？

讨论过程先质疑 Interaction DSL：组件点击与关闭弹窗原本就由组件负责，Definition 里再写事件名称可能没有价值。随后重新评估发现：事件名称本身不值得抽象；Material 事件与另一项受控操作之间的“连接关系”具有独立的配置价值。

场景是否需要 Interaction Binding理由
Select 展开、Popover 关闭、聚焦通常不需要Material 自己完成内部交互
Input 修改绑定值不需要额外 Interaction现有 Binding Adapter → Command 已覆盖
卡片编辑按钮打开另一块独立 View可能需要跨节点连接关系不能总是写死在复合物料内部
通用按钮删除当前数组项适合受限映射可直接复用已有的 Array Remove Command
按钮通知宿主执行保存可选适用只传递声明过的业务意图，不承担保存请求
Material Event
例如 edit
→
View Interaction Binding
edit → Typed Intent
→
View Controller /
Runtime / Host
决策修订

保留 V5，但不建设完整的 View Interaction DSL。V1 仅需按需把 Material 的语义事件映射到有限目标意图，避免任意脚本、请求编排和工作流。

V5 · 有限 Event → Intent 连接

候选 Intent用途由谁执行范围判断
form.command执行第三组已有数据 CommandForm Runtime应支持
view.present展示指定的表单内部视图View Controller应支持
view.dismiss关闭当前呈现的内部视图View Controller应支持
host.emit向宿主发送受限业务意图Host可选，契约待定
Event → Intent · 视图连接
{
  "material": "contact-card",
  "on": {
    "edit": {
      "type": "view.present",
      "target": "contact-editor"
    }
  }
}
Event → Intent · 复用 Command
{
  "material": "button",
  "props": { "label": "添加联系人" },
  "on": {
    "activate": {
      "type": "form.command",
      "command": {
        "op": "array.insert",
        "target": "/contacts",
        "value": { "name": "", "phone": "" }
      }
    }
  }
}

这里不重新发明 Action 体系：form.command 引用既有数据操作；view.present / view.dismiss 只针对表单内部的呈现关系；host.emit 只传受限信号，不能当作任意远程函数调用器。

不在 V1 建设通用 sequence、if/else、async action、RPC 调用链、事件总线、跨业务路由。

12

View Interaction 与 Repeater / Scope

Repeater 是第四组不能完全交给纯视觉物料的例外：它实例化来自 Form Data 的动态数组项，并与第一组的 Scope / Runtime Identity 语义关联。

例如对联系人列表中每一行显示“编辑”和“删除”按钮。Interaction 必须正确定位当前联系人实例，不能把 Definition 编译成固定的 /contacts/0、/contacts/1 作为永久身份。

Repeat 及当前项操作 · 语义示例
{
  "repeat": {
    "collection": "/contacts",
    "as": "contact",
    "template": {
      "material": "contact-card",
      "bind": { "scope": "contact", "path": "" },
      "on": {
        "edit": {
          "type": "view.present",
          "target": "contact-editor",
          "scope": "contact"
        },
        "remove": {
          "type": "form.command",
          "command": {
            "op": "array.remove",
            "target": { "scope": "contact" }
          }
        }
      }
    }
  }
}
协议状态：上例中空 path、scope 传递、array.remove target 的确切形状都未冻结。只确认：必须能够把当前实例 Scope 显式传递给目标 View 或 Command，且不能依赖永久数组索引。

Material Event 可携带类型化 Payload，但事件 Payload 与 Scope 如何合并、如何限制其对目标 Reference 的访问，是本组保留的首要细节问题；不需要因此发明可执行事件脚本语言。

13

V6 · Fragment 作为静态结构复用

独立 Profile 更直观，但可能重复使用相同字段结构。我们接受可选 Fragment，不引入基础视图继承、任意覆盖、树结构 Patch 等复杂机制。

Fragment · 示意，未冻结变量与 Scope 语法
{
  "fragments": {
    "contact-fields": {
      "material": "stack",
      "children": [
        { "material": "text-input", "bind": "/contact/name" },
        { "material": "text-input", "bind": "/contact/phone" }
      ]
    }
  },
  "views": {
    "expanded": { "useFragment": "contact-fields" },
    "compact": {
      "material": "detail-panel",
      "slots": {
        "content": { "useFragment": "contact-fields" }
      }
    }
  }
}

Fragment 只是视图结构复用单元，不默认携带独立 Form Data、独立事务或单独生命周期。其在动态数组中的局部引用，应复用既有的词法 Scope。

方案取舍
每个 Profile 完全复制适合简单场景，始终允许
独立 View + 可选 Fragment推荐 V1 方向
View 继承与结构覆盖不采纳，增加合并顺序、冲突和版本成本

显隐、禁用与校验的关系

View 的展示条件只控制可见性和 UI 交互，并不自动修改 Form Data，也不自动改变 Constraint 的业务合法性。

受控 Dynamic Slot · 示例
{
  "material": "text-input",
  "bind": "/companyName",
  "props": {
    "visible": {
      "$expr": {
        "op": "eq",
        "args": [
          { "ref": "/accountType" },
          "business"
        ]
      }
    }
  }
}
需求明确归属
根据字段值显示或隐藏组件View Dynamic Slot + Expression
隐藏时清空 companyName需要数据联动时显式用 Reaction
隐藏时不校验 companyName需要适用条件时显式用 Constraint.when
禁用 InputMaterial/UI 属性；不是权限或数据删除
同一错误在 PC 字段与手机卡片呈现Validation Issue 绑定数据引用；View 负责呈现方式

不能因为 Compact Profile 没有展示某字段，就使该字段的共享业务约束或数据值失效。

完整组合示例：同一 Data，不同视图与交互

下面给出一份精简的语义级组合示例，用于串起 Profile、Material、Binding、Fragment、Interaction；并不包含前三组已经独立定义的所有校验和业务规则。

组合示意 · 非正式 JSON Schema
{
  "id": "contact-form",
  "data": {
    "schema": {
      "type": "object",
      "properties": {
        "contact": {
          "type": "object",
          "properties": {
            "name": { "type": "string" },
            "phone": { "type": "string" }
          }
        }
      }
    }
  },
  "fragments": {
    "contact-editor": {
      "material": "stack",
      "children": [

Expanded Profile

直接展示联系人编辑字段。字段直接关联 Form Data，不需要 Interaction。

Compact Profile

被否决或明显降级的方案

候选决定原因
所有 Profile 共享一棵树并动态重组不采纳结构差异会引入大量条件和转换规则
View Inheritance + Node Override不采纳配置合并、冲突和升级治理成本高
为所有 UI 元素建立专用 Node 类型不采纳演变为通用页面搭建 DSL
Binding 配置 read / write 逆向映射 DSL不采纳组件输入契约与数据关联混淆
完全禁止声明式 Interaction已修订跨组件连接会重新进入专用物料或宿主代码
完整 View Interaction 工作流不采纳会引入异步操作、条件分支、动作链和页面生成职责
Modal 默认有独立 Draft Data不采纳与默认实时编辑及唯一权威 Work Data 不符
View 隐藏字段即清空数据不采纳破坏 Data / View 独立与共享校验语义
Form Engine 负责请求远程选项不纳入核心资源获取属于 Host / Material Adapter

尤其应当保留的历史修订

V5 不是从“完全不需要”直接变成“完整 DSL 很重要”；实际结论是：内部交互仍属于物料，只有组件边界之外的明确连接关系值得声明。因此保留有限 Event → Intent，而不是全面恢复事件编排。

L1 / L2 / L3 / L4 / Host 职责交接

层次本轮应明确的责任不应该承担的工作
L1 DefinitionView Profile、Material 结构、Binding、Dynamic Slot、Fragment、受限 Intent组件内部事件执行算法与 HTTP 请求

此表是边界约束，不是 Runtime 的时序图。具体 View Controller 是否属于 Renderer 的一部分，由各端实现决定。

用例验收：第四组足够表达什么？

S1 · 普通 CRUD：TextInput 通过 bind 更新单字段；无需独立 Interaction；校验由共享 Constraint 处理。
S2 · PC 平铺 / Mobile 摘要：独立 Profile 指向同一数据契约；Mobile Card 可打开独立详情。
S3 · 嵌套联系人：Repeater 为每项建立 Scope；Material 的编辑/删除意图正确作用于当前项；移动或删除不误绑新索引。
S4 · 数据依赖显隐：动态槽位表达 visible；隐藏不清空数据、不自动停用共享校验。
S5 · 复合物料：DateRange、Card/Editor 可用具名 Binding Port 与 Slots，不需要附加通用逆向写入 DSL。
S6 · 异步外部数据：远程选项由 Host / Material Adapter 管理；选中值仍交由 Runtime 保存。
S7 · Profile 按需交付：客户端只收到选中视图及必要依赖；不因视图裁剪破坏共享 Data / Constraint / Behavior。
S8 · 编辑弹窗：实时修改直接进入 Work Data、共享联动生效；取消若必须回滚，另列 Editing Context 需求。

这些是后续正式协议和 L2/L4 实现必须通过的场景，不代表已经编写自动化测试。

正式记录：第四组阶段性决策

ADR-04 · 阶段性定稿

View Definition 负责多 Profile 视图组织、Material 组合、统一数据 Binding、受控动态属性和可选的有限 Event → Intent 映射；Renderer 实现内部交互，Host 管理外部副作用。所有表单业务数据以单一 Work Data 为权威，移动端详情编辑默认实时生效。

01

多端视图独立

每个 View Profile 可有完整独立视图树，并支持 Profile 级按需交付。

02

视图结构轻量化

Material 组合为主，只保留 Repeat / Scope 等必要的表单语义。

03

Binding 最小职责

负责关联数据，不复制组件内部读写实现或表达式逆向赋值。

04

内部交互留给组件

Select、Modal 内部开关、焦点等不写入 Form Definition。

05

保留受限交互连接

Material Event 按需映射到已有 Command、内部 View 呈现或受控 Host 意图。

06

局部状态与业务数据分离

View State 属于 Renderer，业务数据进入唯一 Runtime；Modal 默认实时编辑。

07

不拓展为低代码页面系统

不支持任意页面导航、异步编排、通用脚本、完整 UI 继承覆盖体系。

归档状态：第四组 L1 能力边界已收敛；候选 DSL、事件参数、目标引用和交付 API 尚未冻结。
