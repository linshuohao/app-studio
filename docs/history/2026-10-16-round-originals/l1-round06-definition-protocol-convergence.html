03

架构分层与两条“不可越界”红线

Conceptual flow / 概念关系
L1 Canonical Form DefinitionData / Expression / Constraint / Reaction / View / Interaction
↓
L2 Preparation规范化、静态分析、Scope 绑定、依赖、Profile 选择、能力检查
↓
L3 Form Runtime唯一 Work Data / 稳定 Item Identity / Command / 同步 Reaction / Validation
↓
L4 Renderer & Material + Host展示容器、组件交互；外部校验、提交和其他业务请求
红线 01：单一数据源

PC、移动端卡片与弹窗默认编辑同一份 Form Working Data；UI 临时状态不是第二份业务数据。

红线 02：不扩张成低代码工作流

External Constraint 不发请求；Reaction 不等待外部 Promise；Modal/Drawer 不要求核心 View Action Engine。

对象类型解析失败、同步约束失败、外部校验失败属于不同层次。引擎不能把“业务校验不通过”简单转化成“所有联动停止”。

04

顶层 Form Definition：单一逻辑文档

结构草案 · 非冻结类型
interface FormDefinition {
  protocolVersion: string;
  id: string;
  version: string;

  data: DataDefinition;
  expressions?: Record<string, Expression>;
  constraints?: Constraint[];
  reactions?: Reaction[];
  views: Record<string, ViewProfile>;
  viewTemplates?: Record<string, ViewTemplate>;
  metadata?: Record<string, unknown>;
}

Schema 为数据结构的权威来源。expressions 是可选的命名复用入口；Constraint、Reaction 作为规则条目具有身份；View 是独立 Profile。viewTemplates 只在结构复用时需要。

未设立的顶层模块

不新增 resources、services、actions、lifecycle、submitWorkflow、presentation、inputBuffers。讨论过实例能力，并不意味着一定要成为配置字段。

“单一逻辑定义”不等于只能存一个物理 JSON 文件。设计器可拆分管理，但发布时必须能够形成有明确版本的完整逻辑 Definition。

06

Reference：数据寻址的唯一规则

所有 Data、Expression、Constraint、Reaction、Command、View Binding 使用统一寻址语义，但各位置允许访问的 Source 和权限不同。

Reference · 候选 Canonical 形式
{ "source": "data", "path": "/applicant/name" }
{ "source": "data", "scope": "insured", "path": "/age" }
{ "source": "context", "path": "/locale" }
{ "source": "event", "path": "/selected" }
路径明确含义
""根值（JSON Pointer）
"/"名称为空字符串的属性，不是根
"/a~1b"属性名 a/b
"/a~0b"属性名 a~b
"/insureds"Data Root 的 insureds 属性，当前局部 Scope 不改变它的含义

根路径短写默认指向 Form Data Root；局部数据使用明确的 scope。不允许在某个 Repeater 内让同一个 "/name" 自动从根引用变成当前行引用。

Scope 的权责：来源、绑定、实例三分离

Conceptual flow / 概念关系
Data Schema + Form Working Data结构与实际数据唯一来源；不单设 data.scopes 顶层表
↓
局部 ScopeBinderView / Reaction / Constraint 的限定结构位置声明 from + as + mode
↓
L2 Lexical Compiler类型检查、词法别名与可见性、编译期绑定 ID
↓

Scope 不是独立 Store、不是另一个全局命名空间，也不是只有 View.repeat 才能创建。View 和 Reaction 可以有各自的词法绑定帧，但不能产生两套互相独立的业务实例身份。

概念谁定义/拥有意义

08

统一 ScopeBinder：对象与集合项

最小 Binder 候选结构
type ScopeBinder = {
  from: DataReference;
  as: string;
  mode?: 'one' | 'each';
};
type ScopeDeclaration = ScopeBinder | ScopeBinder[];
mode: one · 默认

绑定确定的数据位置。独立对象 /applicant 可以绑定为 applicant，不要求写所有字段的完整根路径。

mode: each · 集合

针对数组每一项建立局部环境。View 中逐项实例化子树；Reaction / Constraint 中逐项应用规则。

多层数组的有序词法绑定链
{
  "scope": [
    { "from": "/applicants", "as": "applicant", "mode": "each" },
    {
      "from": { "source": "data", "scope": "applicant", "path": "/insureds" },
      "as": "insured",
      "mode": "each"
    }
  ]
}
  • 只允许在结构性边界引入：View 的 ScopeNode、规则入口；Expression、Command 和普通 Props 只能使用既有绑定。
  • 同一词法链建议不允许重名遮蔽；没有 from 的绑定声明应被拒绝。
  • from 不接受任意 Expression 动态计算数据路径；若当前引用不存在或类型不符，不自动创建数组/对象。
  • 多处使用相同别名或 from 不等于多份数据或多个独立 Scope Registry。
已比较并倾向放弃：全局 scopes Registry

集中声明所有对象/集合能减少少量 from 的重复，却引入命名、嵌套关系、Schema 重复维护和跨片段耦合。局部词法绑定 + L3 统一实例身份更适合当前的最小协议。

09

ScopeHandle、事件参数与跨视图传递

Data Reference 取得业务值，ScopeHandle 表示当前实例定位身份；两项数据值完全相同的数组成员仍然是两个不同实例。

ScopeHandle 不等于业务值
// 当前联系人数据值：
{ "source": "data", "scope": "contact", "path": "" }

// 当前联系人实例句柄：
{ "$scope": "contact" }

// 在集合操作中精确指向当前项：
{
  "op": "array.remove",
  "target": "/contacts",
  "item": { "$scope": "contact" }
}

Interaction 的临时环境包含两部分：Material 的事件参数（可由 source:event 读取），以及当前结构性 Scope 捕获。某个事件的 Payload 可能为空，但它发生在特定被保人卡片内，其实例定位仍然可用。

事件 → Command · 当前行定位
{
  "on": {
    "remove": {
      "type": "form.command",
      "command": {
        "op": "array.remove",
        "target": "/insureds",
        "item": { "$scope": "insured" }
      }
    }
  }
}

内部 Handle 不应被当作普通可序列化业务 ID 发送给外部服务；Host 需要外部调用时，应明确取得业务值与业务标识，并在异步返回后核对当前实例是否仍然有效。

Expression：一套纯 AST + 递归动态值

第二组已经确定 Expression 为 JSON AST，Pure Function 为已注册的纯同步能力。第六组的重要修订是：ValueSpec 的嵌套结构默认递归识别显式 $expr 标记，不对每个深层 Material Props 再维护动态字段白名单。

在 ValueSpec 中任意深度发现显式 Expression
{
  "props": {
    "badge": {
      "visible": {
        "$expr": {
          "op": "eq",
          "args": [{ "ref": "/country" }, "JP"]
        }
      },
      "label": { "$expr": { "ref": "/status" } }
    }
  }
}
语义位置建议写法解释
constraint.assert / reaction.whenExpression AST（可直接写）槽位类型本身已确定
material.props / command.value递归 ValueSpec；嵌入 $expr允许静态 JSON 和动态节点混合
静态配置值中确实有 $expr 形状显式 $literal 或等价转义保留普通 JSON 数据原样
Material ID / 引用目标 / 规则 ID结构性静态字段L2 检查，不因为递归发现就支持动态结构名
递归识别 ≠ 猜测

只有规范的显式包装会被识别；任意 {"op":"eq"} 对象不是自动 Expression。Data Schema 的 default、Working Data 和不属于 ValueSpec 的外部原始 JSON 不能无差别扫描并执行。

命名 Expression 可以复用，但 V1 不允许全局命名表达式隐式捕获调用者的局部 Scope。局部逻辑优先内联，避免引入动态作用域或参数化函数系统。

Constraint：内部断言、外部校验义务

Internal Constraint · 条件检查（片段）
{
  "id": "insured-age-range",
  "kind": "internal",
  "scope": { "from": "/insureds", "as": "insured", "mode": "each" },
  "assert": {
    "op": "gte",
    "args": [
      { "ref": { "source": "data", "scope": "insured", "path": "/age" } },
      18
    ]
  },
  "issue": {
    "target": { "source": "data", "scope": "insured", "path": "/age" },
    "code": "AGE_TOO_LOW"
  }
}
External Constraint · 声明义务而非网络调用
{
  "id": "insured-eligibility",
  "kind": "external",
  "scope": { "from": "/insureds", "as": "insured", "mode": "each" },
  "dependsOn": [
    { "source": "data", "scope": "insured", "path": "/age" },
    { "source": "data", "scope": "insured", "path": "/idNumber" }
  ],
  "target": { "source": "data", "scope": "insured", "path": "/idNumber" },
  "requiredForSubmit": true
}
问题结论
Expression 无法解析传播不可求值/诊断；不得偷换为布尔 false 或旧值
同步 Constraint 不通过记录问题，不默认阻断其他数据 Reaction
外部校验未执行Unverified，不等价于通过
外部校验 Pending / Invalid / Error不满足必需提交校验；不自动等待或重启 Reaction
条件约束的 when决定约束适用性；无法求值不能视为自动通过

Constraint 不直接执行 onFail Command。需要影响数据时，应通过独立 Reaction 条件或 Host 在外部完成必要验证后发出 Command。

12

外部校验状态、有效性与 Readiness

状态语义是否满足必需校验
unverified当前适用输入尚无有效结论否
pendingHost 报告正在执行否
valid当前输入存在有效通过结论是
invalid当前输入业务校验失败否
error校验执行错误，不能判断合法性否

每项外部结果至少关联 Form Instance、Constraint ID、Scope Instance、所依赖数据的有效性标识及调用身份。输入依赖变化后，旧结论应立即失效；与校验无关的字段修改不必使其失效。

Conceptual flow / 概念关系
Definition / Host 注册外部校验义务由 dependsOn 指出适用的数据依赖；Host 可补充宿主特有义务
↓
Host 执行并报告状态网络、重试、防抖等都不由引擎负责
↓
L3 被动登记 / 检查结果是否仍适用于当前数据不接受过期 Invocation 对当前值的错误覆盖
↓
Validation Readiness内部约束与规范化输出成功 + 所有已注册且适用的必需外部约束 valid
↓
Host 最终决定提交再次核对一致数据版本，再进行权限和业务检查、HTTP 提交
关键边界

Readiness 只涵盖 Runtime 已知的校验义务，不是对 Host 所有业务规则的全知判断。服务端业务事实在数据不变时也可能变化，Host 需负责有效期、重新验证或主动撤销结论。

外部校验结果不会自动恢复某个先前因类型失败而没有执行的 Reaction；如外部结果需要回填城市、资格或保费，Host 明确发出普通 Command，Runtime 再执行同步联动。

13

Command：封闭的结构化数据修改

操作受控语义
set设置/替换目标值，目标对象未指定键不会被隐式保留
patch局部修改指定对象属性；初版倾向浅 Patch，不递归深合并
remove移除对象属性或指定数据位置，具体合法目标有待正式类型收敛
array.insert插入数组项
array.remove删除指定项，模板中可通过 ScopeHandle 定位
array.move移动数组项并保留运行时稳定身份
batch对受控操作做显式组合；Reaction.then 可直接是 Command[]
Command.value 直接使用 ValueSpec
{
  "op": "set",
  "target": "/order/total",
  "value": {
    "$expr": {
      "op": "mul",
      "args": [{ "ref": "/order/price" }, { "ref": "/order/quantity" }]
    }
  }
}

Command Target 限制为可修改的 Data Reference，不能写入 Context 或 Event，也不支持任意 Expression 动态生成修改路径。Command 本身不调用 HTTP，不允许注入任意脚本或自定义执行器绕过 Runtime。

14

Reaction：watch / when / then 的语义边界

同步规则片段
{
  "id": "clear-insured-city",
  "scope": { "from": "/insureds", "as": "insured", "mode": "each" },
  "watch": [
    { "source": "data", "scope": "insured", "path": "/country" }
  ],
  "then": [
    {
      "op": "set",
      "target": { "source": "data", "scope": "insured", "path": "/city" },
      "value": null
    }
  ]
}
  • watch 是明确的变化触发源，可监听多个 Data Reference；when 是触发后的可选纯条件。
  • when 读取的其他依赖，不能被 L2 擅自添加到 watch 里而改变业务触发语义。
  • then 直接保留有序 Command[]，不强制套一层无额外价值的 Batch 包装。
  • 字段业务校验不通过不意味着整个 Form 的所有 Reaction 都停止；只有依赖无法求值时，相应的修改才不能产生有效 Command。
  • Reaction 只处理同步内部数据联动；不等待外部校验，也不订阅视图临时 UI 事件。
执行调度已移出 L1

Change Detection、触发队列、去重、循环保护、候选状态与一次稳定发布，属于 L3。L1 只定义行为的可观察语义与受控数据修改意图。

View：Material 必须包含容器与复合业务组件

本轮 View 讨论有一次重要修订：原先把 Modal、Drawer 当作特殊 Presentation Mode，后根据 C 端交互多样性的要求，统一归入 Material 体系。

Material 类别例子自身职责
输入Input / Select / DatePicker编辑交互 + Binding Adapter
展示Summary / Price / BenefitCard读取数据 / UI 展示
布局Stack / Grid / Section组合 Slots
容器Modal / Drawer / BottomSheet / Popover打开关闭、Portal、动画、遮罩、焦点和 UI 局部状态
复合业务InsuredEditor / AddressPicker封装复杂视图与内部交互
操作Button / ArrayAdd语义事件，必要时连接 Command 或 Host

只要一个 Material 能通过 Props、Binding 和 Slots 自行完成相关交互，L1 就不重复定义打开、关闭、抽屉层级或 UI 事务。

正式修订

移出核心：view.present / view.dismiss / 独立 Presentation Spec。它们不是概念上绝无价值，但目前不足以抵消新增 View Controller、跨树实例身份与 UI Action 调度的成本。

16

ViewNode：MaterialNode / ScopeNode / Template Use

ViewNode 概念类型 · 待冻结字段
type ViewNode = MaterialNode | ScopeNode | TemplateUse;

type MaterialNode = {
  material: string;
  props?: Record<string, ValueSpec>;
  bind?: DataReference | Record<string, DataReference>;
  children?: ViewNode[];
  slots?: Record<string, ViewNode | ViewNode[]>;
  on?: Record<string, InteractionIntent>;
};

type ScopeNode = {
  scope: ScopeDeclaration;
  node: ViewNode;
};

type TemplateUse = {
  $use: string;
  with?: Record<string, ScopeHandleReference>;
};

动态集合的 View 重复实例化直接由结构性 ScopeNode.scope.mode = "each" 表达，父级 Material 不需要再写 repeat，也不需要给每类组件实现自己的 Scope。

一处结构语义同时完成每项绑定与重复实例化
{
  "scope": { "from": "/insureds", "as": "insured", "mode": "each" },
  "node": {
    "material": "insured-card",
    "bind": { "source": "data", "scope": "insured", "path": "" }
  }
}

ScopeNode 是引擎能理解的结构包装，不应与 material.props.scope 混用。子树实例化是 View 消费该 Binder 的含义；Reaction 中相同 Binder 的含义是逐项适用规则。

17

Binding、Slots 与 Material Manifest

Binding 只声明关联哪份数据，不再以 read/write DSL 重复描述组件的更新行为。普通 Input 由 Material Adapter 更新 Runtime；展示物料可读取同一 Reference；UI readonly 是物料属性，不代表 Host 数据权限。

默认 Binding Port 与具名 Port
// 单字段 Binding：
{ "material": "text-input", "bind": "/applicant/name" }

// 多字段复合 Binding：
{
  "material": "date-range",
  "bind": { "start": "/startDate", "end": "/endDate" }
}

children 建议只是 slots.default 的 Authoring 简写。对有多个插槽的复合物料，使用 slots.trigger、slots.content 等明确 Slot。禁止同一节点重复提供 children 和 slots.default。

Manifest 概念契约
interface MaterialManifest {
  id: string;
  propsSchema?: JsonSchema;
  bindings?: Record<string, { valueSchema: JsonSchema }>;
  slots?: Record<string, { cardinality: 'one' | 'many' }>;
  events?: Record<string, { payloadSchema?: JsonSchema }>;
}

Material 事件元数据用于类型检查、工具提示和选择性外部连接；并不代表所有内部点击、开合和手势都必须在 Definition 的 on 中声明。

18

View Profile、Named Template 与 $use 的真实含义

原先曾设计 Profile 下的 root + targets，另有全局 fragments；讨论发现它们都在重复定义同一种 ViewNode 内容，因此收敛为：Profile Entry + 可选 Named View Template + Template Use。

Profile Entry 选择内容，Template 按需定义
{
  "views": {
    "expanded": { "entry": { "$use": "expanded-form" } },
    "compact":  { "entry": { "$use": "compact-form" } }
  },
  "viewTemplates": {
    "expanded-form": { "node": { "material": "stack", "children": [] } },
    "compact-form":  { "node": { "material": "stack", "children": [] } }
  }
}

$use 是静态结构引用，不是 DOM 替换命令、不是动态模板切换，不默认共享 React/Vue/Flutter 组件实例或 UI 局部状态。L2 可以展开或保留已解析引用；L4 按当前位置建立视图实例。

同一 Template 在 PC 内嵌和移动端弹层中使用，复用的是视图定义，不共享 Modal 的打开状态、焦点或滚动位置。但两处字段都绑定到同一个 Form Working Data。

Fragment 的边界

Fragment 不再需要独立领域注册表；通过 Named Template 复用即可。模板若需要局部 Scope，显式声明参数、由调用者提供 Handle，不隐式捕获外部局部变量。模板不能递归无限嵌套，L2 应检查引用环。

19

容器交互：从 view.present 回归 Material 内聚

容器物料负责呈现

Modal、Drawer、BottomSheet 的开闭、Portal/Teleport、视觉与局部 UI 生命周期由对应 Material 自己实现。

View 协议只传内容

外层容器通过 trigger/content 等 Slots 接收视图定义；内部结构可用同一模板复用。

容器负责内部交互；Slot 契约由物料声明
{
  "material": "bottom-sheet-editor",
  "slots": {
    "trigger": {
      "material": "insured-summary",
      "bind": { "source": "data", "scope": "insured", "path": "" }
    },
    "content": {
      "$use": "insured-editor",
      "with": { "insured": { "$scope": "insured" } }
    }
  }
}

上述配置成立的前提是 bottom-sheet-editor 自身定义 trigger Slot 如何打开 content。Slot 名称不会自动赋予点击行为。

已知限制与可选扩展方向

两个完全无父子关系的物料要在纯 Definition 中实现跨树 UI 协作，容器自身状态可能不够。V1 先通过复合容器 Material 或 Host 进行协调；只有大量实际需求出现，才重新评估可选 UI State / Action 扩展，而不是提前恢复通用 view.present。

Interaction：保留受限 Event → Intent

映射执行方保留原因
form.commandForm Runtime普通 Button/Card 触发封闭 Command，不需为每个数据操作造专有物料
host.emitHost需要跨业务外部能力时进行有类型、有授权的意图通知
view.present / view.dismiss不纳入 V1 核心展示编排由容器物料承担，避免第二套 UI Action Engine
宿主意图映射
{
  "material": "button",
  "props": { "label": "提交" },
  "on": {
    "activate": {
      "type": "host.emit",
      "event": "insurance.submitRequested"
    }
  }
}

普通字段修改仍优先由 Binding Adapter 处理，不要求每次 change 再声明 form.command，以免双重写入。Event Payload 如需映射到 Command Value，可以在 Interaction 内通过 source:event 的 Expression 使用。

反应边界：Interaction 是组件事件的连接关系，Reaction 是 Form Data Change 驱动的数据联动。两者共享 Command，但不合并为同一个异步通用 Behavior DSL。

Host Integration：三条调用路径

调用类别Definition 中如何表达谁决定调用时机
外部校验kind: external 的 Constraint + dependsOnHost 根据数据变化、策略或提交需要执行 Validator

物料内部需要远程资源Material Contract / Host Service 注入Material Adapter 自己调用，而不是把每次请求写成表单行为
Host 能力是运行环境契约
// Host 接口形状，仅示意，不要求变成 Definition 顶层服务表：
interface FormHost {
  validators?: Record<string, ExternalValidator>;
  events?: Record<string, HostEventHandler>;
  services?: Record<string, HostService>;
}

// 外部副作用完成后，如果需要更新表单：
form.dispatchCommand({ op: 'patch', target: '/address', value: result });
  • Host 的能力是否存在、参数/输出是否匹配，需要显式校验；未知的必要能力不能静默放行。
  • Definition 写了一个事件名，不等于获得相应权限。Host 和服务端必须做授权与参数校验。
  • 与特定物料内部行为紧密相关的请求，可直接通过注入服务调用，不强制走 host.emit。
  • 不新增一个统一的 Resource/Provider/Service/Action 工作流定义模块。

按 View Profile 交付和完整规则保留

Conceptual flow / 概念关系
Canonical Definition全部 Profile、共享 Data Schema、Constraint、Reaction 与命名资源
↓
L2 选择 Profile 并解析它引用的模板编译 Scope/Reference/Expression；检查 Material / Pure Function / Host 所需能力
↓
Target Bundle仅交付当前 Profile 的必要视图；保留正确执行表单所需的业务语义

讨论中的架构修订记录

ValueSpec 递归 Expression物料无需单独动态属性白名单要定义安全的 Literal 转义和结构字段限制
封闭 Command + 同步 Reaction变更入口受控、可追踪与验证未来任意脚本扩展不如通用工作流灵活
Material 包含容器与复合组件C 端视觉/交互扩展不改核心协议某些跨树纯配置协调需 Host 或复合容器
View Template 纯结构复用重复视图少，状态所有权清楚需检查引用环、参数、Scope 兼容
外部校验状态被动登记完整判断必需校验是否完成Host 与 Runtime 需要身份和有效性契约
Profile Bundle减少无关 View 下发并检查端能力Preparation 需要分析模板与依赖闭包

上述“成本”为相对架构与维护复杂度判断，不是实际人力或金钱报价。本轮没有基于工程实测提供工时数字。

不纳入核心的设计与对应替代

不纳入核心替代与原因
通用 Resource / Query SchedulerHost、Material Services；不会让 Form Engine 负责网络缓存重试
Async Reaction / Action WorkflowHost 等待外部结果并通过 Command 修改数据
独立 Input Buffer / 普遍 Modal Draft唯一 Work Data；输入法等 UI 临时状态留给 Material
View Presentation Engine / view.present容器 Material + Slots；跨树协作可由 Host 承担
FieldNode / ModalNode / DrawerNode 等大量类型MaterialNode + ScopeNode + TemplateUse
全局数据 Scope Registry局部 ScopeBinder + L3 统一实例身份
任意自定义 Command 执行器封闭结构化数据修改集合
完整 Submit WorkflowHost 使用一致的校验和规范化输出契约

例如取消 view.present 不等于不能做弹窗，而是让弹窗由容器 Material 提供。同理，取消 Resource 定义不等于不能远程加载选项。

最终摘要：第六组的核心收敛

DATA
Data Schema 定结构，Form Runtime 只有一份 Working Data移动端弹窗默认实时编辑；UI 局部状态不成为第二份业务数据
SCOPE
ScopeBinder 可局部声明，但实例身份由 L3 统一one/each 复用相同语义；不建立全局 Scopes Registry
EXPR
一套纯 Expression AST，ValueSpec 递归识别显式 $expr不推断普通 JSON、不执行任意脚本
RULES
Constraint 产出合法性结论；Reaction 负责同步数据联动外部校验不阻塞或恢复同步 Reaction
COMMAND
受控封闭数据修改，唯一写入入口set/patch/array 操作；Command 不承载 HTTP
VIEW
Profile + MaterialNode + ScopeNode + TemplateUse容器也是物料，Template 只是静态结构复用
HOST
外部约束、host.emit、Material Host Service 三种清晰路径Readiness 由 Runtime 汇总已知义务，最终提交由 Host 决策
我们设计的是“可组合、可跨端、职责清晰的复杂表单定义协议”，不是“可以通过 JSON 驱动所有页面、请求与业务流程的通用低代码系统”。

本档案建议与第一至第五组 ADR 配套使用。若后续具体 Schema 细节改变，应优先检查是否破坏这里已收敛的领域语义，而不是通过新增隐式规则维持旧示例。
