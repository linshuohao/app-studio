# Platform / Studio · 内置访问与首次保存

> 待总协调会话评审。切片范围已授权，以下实施建议与待决契约需按各自状态处理。

## Why

让首位管理员从空库开始，完成受控初始化、登录、创建表单、保存配置及重新打开。通过真实持久化验证表单和配置版本的归属、不可变性以及重试语义，为配置历史、检查预览、发布和 GitHub 登录提供后续接缝。

[现行创作 MVP](../../../docs/design/platform-studio.md#platform-authoring-mvp)与 [ADR-FE-029](../../../docs/design/decisions/ADR-FE-029-platform-config-versions.md)定义保存和版本语义，[确认记录](../../../docs/design/source-map.md#src-platform-simplified)定义四个交付切片。首期表单直接组织配置版本，草稿留在编辑器，最近保存提供默认编辑起点。ADR-FE-028 已由 ADR-FE-029 替代，分支、分支指向与覆盖确认均已移出首期。访问沿用[单团队 RBAC](../../../docs/design/platform-studio.md#platform-rbac)和 [ADR-FE-026](../../../docs/design/decisions/ADR-FE-026-platform-rbac.md)，模块边界沿用 [ADR-FE-027](../../../docs/design/decisions/ADR-FE-027-platform-modular-monolith.md)。按[项目 OpenSpec 工作流](../../../docs/design/workflows.md#workflow-openspec)评审，现行契约以这些来源为准。

## What Changes

### 本轮范围

- 受控建立唯一默认空间、首个内置用户及其管理员成员资格。支持内置凭据登录、退出和读取当前访问上下文。服务端按有效用户、成员、业务权限、资源归属和业务条件校验请求。查看权覆盖列表和打开，编辑权覆盖创建和保存。
- 交付最小 Studio 路径，登录后可列出、创建并打开表单。创建仅生成稳定的 `formId` 和表单记录。无配置版本时，编辑器加载统一初始文本。
- 工作台支持原始文本保存、结果反馈与重开。首次及后续独立成功保存各生成一个 `versionId`，记录原文、表单、保存人、时间和可选来源。允许无法解析的 JSON。来源属于同一表单，只供追溯，两个从同一来源发起的独立保存均可成功。重开读取确定的最近保存版本。
- 同一创建或保存请求的幂等重试返回原结果。保存成功只确认该次发送的文本，提交期间的后续编辑保持未保存。保存失败或撤权时保留本地文本，离开工作台前提示尚未保存的内容。

### 本轮排除

GitHub 登录与绑定、公开注册、密码找回、成员或角色管理 UI、多空间 UI、表单重命名、复制、归档操作与历史浏览页。服务端仍需拒绝对归档表单的常规保存。检查、预览、发布、Host 在线装载、能力资产后台、可视化设计和实时协作由各自切片承接。

### 实施建议

| 环节       | 首轮建议                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 受控初始化 | 使用部署操作者显式调用的一次性本地命令，通过受控输入接收初始凭据。以同一事务建立默认空间、用户、凭据和管理员成员资格，以数据库约束抵御并行初始化。后续执行报告已初始化，既有账号、密码和角色保留。                                                                                                                                                                                                           |
| 内置访问   | 成员访问模块拥有用户、凭据、成员及会话。凭据以独立记录关联稳定用户 ID，存储带盐的密码哈希。建议同源 Studio 入口使用 HttpOnly Cookie 携带不透明随机令牌，服务端持久化令牌摘要、归属、到期与撤销状态。退出撤销当前会话并清除 Cookie。未过期且有效的会话可随 API 重启恢复。HTTPS 使用 Secure，写操作检查来源并防止 CSRF。访问上下文返回用户、默认空间及有效权限所需的最少信息，每次受保护请求重新校验当前资格。 |
| 最小持久化 | 建议首轮以单实例 Nest API 和挂载在持久目录的 SQLite 文件验收。用迁移管理默认空间、用户和凭据、成员和角色、会话、表单、配置版本及请求幂等记录。表单创作模块负责写表单及版本，并提供按表单和版本读取确定原文的模块接口。保存事务检查表单状态和来源归属，并按表单分配稳定的追加次序，用该次序查询最近版本。归档切片沿用该写入边界。数据库时间用于追踪，来源版本用于追溯。                                       |
| 幂等与重开 | 建议在通过当前授权后，以空间、操作者、操作及客户端请求键定位幂等记录。创建或保存的写入与结果引用同事务提交。相同键和相同输入重放原结果，即使该版本之后已有更新。相同键配不同输入返回冲突，响应丢失或超时可用原键重试。每次独立提交生成新键，即使文本相同也追加版本。                                                                                                                                         |

## Impact

### 依赖与实现影响

- [Nest API](../../../services/api/src/app.module.ts)的模块装配目前仅有脚手架，[现有 API 集成测试](../../../services/api/test/app.e2e-spec.ts)只验证根路由。建议在同一部署中接入成员访问、表单创作与迁移，复用现有 API 集成测试入口。前端建议由独立 Studio 应用承载登录、列表和文本工作台，现有 [Playground](../../../apps/playground/README.md)用于引擎演示。验收环境需提供 API、Studio 同源访问路径及跨进程重启保留的数据库目录。
- 后续 GitHub 登录依赖可复用的用户身份、访问上下文和会话建立入口，绑定后的身份仍使用同一成员与角色判断。会话建议预留凭据来源的可追溯性，供 GitHub 提案决定解绑时的撤销范围。历史与检查预览依赖准确读取指定 `versionId` 的原文。发布依赖表单归属、不可变版本和最新资格检查接缝，仍需另行确定提交时复核。Host 继续消费 `releaseId`。本轮原文保存无需 Compiler、Runtime、Renderer、物料或 Host 参与。
- 预计影响 API 模块、Studio 应用、持久化迁移、工作区开发与测试入口。后续按实际实现路径补齐受影响消费者与验证命令。

### 可测验收

| 场景                         | 观察结果                                                                                                                                                                                                              |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 空库初始化、重复与并发初始化 | 经授权的操作者建立一组空间、用户和管理员成员资格。重复或并发执行保留唯一一组，失败中途无部分初始化。匿名访问登录接口不能创建管理员。                                                                                  |
| 登录、访问上下文与退出       | 错误凭据无法取得会话。有效凭据返回可访问的默认空间和相应权限。退出后，用原令牌重放列表或保存请求被拒绝。                                                                                                              |
| 列表、创建、首次保存         | 登录后可创建并列出表单。新表单初次打开为统一初始文本，未产生版本。保存含多行、空白和错误 JSON 的原文，返回首个 `versionId`，重开恢复完全一致的文本。                                                                  |
| 两次独立保存                 | 从首个版本发出两个不同请求键的保存，使用相同的来源版本与相同的原文也分别成功。得到两个新 `versionId`，原版本保留，重开加载追加顺序靠后的版本。                                                                        |
| 重试及部分失败               | 并发重放同一保存请求仅新增一条版本，响应丢失后重放返回原 `versionId`。创建重试只保留一个 `formId`。注入事务提交前失败，复核业务写入与幂等记录一并回滚，重试可正常完成。按建议方案，复用同一键修改输入时拒绝且无新增。 |
| 越权与非法保存               | 匿名或会话失效时拒绝列表、打开、创建和保存。使用测试夹具覆盖停用成员、查看者、其他空间资源、归档表单、无效来源和超限输入。查看者可读，编辑请求被拒绝。被拒绝的请求及重试均无新增版本，也不返回越权内容。              |
| 保存期间继续编辑             | 推迟保存响应，提交后继续编辑。收到成功响应时保留后续输入和未保存状态。模拟保存失败或撤权，原编辑文本仍在页面中。                                                                                                      |
| 重启恢复                     | 完全停止并重新启动 API，使用同一持久目录。通过内置账号访问原表单和最新版本，校验旧版本及原文保留。重放最近一次成功请求返回原 `versionId`。若采用建议的持久会话，另验证有效会话延续以及已退出会话维持撤销。            |

实施时以 API 集成测试覆盖鉴权、并发、事务与重启，入口为 `pnpm --filter @form-engine/api test:integration`。以 Studio 浏览器用例覆盖登录、列表、创建、首次及后续保存、重开和未保存状态。

### 风险与待决点

1. **持久化部署边界。** 请协调会话确认首轮能否按单实例及持久文件目录验收。若首轮要求多实例或目标环境无法提供持久卷，需先选用共享事务数据库。数据库驱动、表名和迁移工具可在部署边界确认后细化。
2. **共享访问契约。** 建议采用持久化服务端会话和同源 Cookie。需确认 Studio 与 API 的部署边界、会话有效期及是否要求未过期会话跨重启延续。业务数据重启恢复始终为本轮验收项。访问上下文、登录失败、会话失效和撤销反馈应与后续 GitHub 登录提案协调。初始化命令的具体名称和参数组织可在既定受控边界内细化。
3. **共享写入契约。** 重试去重已确认。建议在本轮为成功创建与保存持久保留请求键和结果引用，并拒绝同键异参。需确认客户端可依赖的重试期限、冲突反馈及错误响应约定，供复制和发布提案参考。需在接口细化时给出统一初始文本及输入大小上限，使 UI 与 API 验收使用同一规则。
4. **交付风险。** 初始化竞态可能产生额外管理员。授权旁路可能暴露他人配置。并发写入、响应丢失或进程重启可能重复追加或读回错误版本。用数据库唯一约束、事务、受保护读取、真实存储的并发与重启反例分别验收。

## 协调评审 · 2026-11-11

通过首轮实施范围评审。以单实例本地部署和持久目录为本轮验收环境，采用 SQLite 与同源服务端会话。数据与有效会话应能随重启恢复。该选型限定首轮环境，部署侧共享数据库另按实际需要处理。

保存和创建的幂等结果随记录持久保留。同键异参拒绝，同键同参仅在当前访问校验通过后返回原结果。稳定用户、成员、会话签发、版本精确读取和归档写入边界是后续切片接缝。会话记录登录来源以供 GitHub 解绑设计消费。跨领域授权、事务及浏览器联验列入后续规格和任务，提案评审不代替这些证据。
